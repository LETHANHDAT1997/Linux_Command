picamera2 + OpenCV: Cầu Nối Đến AI

Tài liệu quan trọng nhất trong bộ 4 phần — vì đây là mảnh còn thiếu ở cả 5 file gốc. picamera2 né toàn bộ vấn đề routing/Media Controller đã vật lộn ở Phần 2 & 3, và đưa thẳng numpy array vào tay bạn để bắt đầu xử lý ảnh/AI.

01Tại sao picamera2

Toàn bộ khó khăn ở Phần 2 & 3 xoay quanh một vấn đề: RPi5 CSI cần libcamera để hoạt động đúng, nhưng V4L2/ffmpeg thuần không nói chuyện được với libcamera. picamera2 chính là libcamera — không phải một lớp giả lập (như libcamerify), mà là binding Python chính thức của thư viện đó.

Đây là con đường ngắn nhất: picam2.capture_array() → numpy array → thẳng vào cv2 hoặc bất kỳ model nào nhận numpy/tensor. Không cần hiểu Media Controller, không cần debug routing ioctl. Phần 1-3 vẫn quan trọng để hiểu vì sao mọi thứ hoạt động — nhưng để bắt đầu code AI ngay hôm nay, bắt đầu từ đây.

03Capture cơ bản: numpy array trực tiếp

python
import time
from picamera2 import Picamera2

picam2 = Picamera2()
picam2.start()
time.sleep(1)          # cho AE/AWB ổn định trước khi lấy frame đầu

array = picam2.capture_array("main")
print(array.shape, array.dtype)   # ví dụ: (480, 640, 4) uint8 — mặc định XBGR8888

Chỉ 4 dòng để có numpy array — không device node, không ioctl, không Media Controller. "main" là tên stream mặc định luôn tồn tại; có thể bỏ tham số này nếu chỉ có 1 stream.

⚠️ Mặc định trả về 4 kênh, không phải 3

Không cấu hình gì thì format mặc định thường là XBGR8888 — 4 kênh (thêm 1 kênh padding/alpha không dùng), không phải 3 kênh BGR mà OpenCV quen dùng. Mục 4 dưới đây chỉ cách cấu hình đúng ngay từ đầu để tránh phải cắt kênh thủ công (array[:,:,:3]).

04Format đúng cho OpenCV chi tiết dễ bỏ sót

picamera2 đặt tên format theo quy ước của libcamera/DRM fourcc — ngược trực giác so với những gì lập trình viên OpenCV quen thuộc.

🎯 Quy tắc vàng

Muốn mảng pixel theo đúng thứ tự (B, G, R) mà OpenCV mặc định dùng, phải chọn format tên là "RGB888" — không phải "BGR888" như trực giác sẽ đoán. Đây là quy ước đặt tên chính thức của picamera2, đã xác nhận trong tài liệu hãng — không phải lỗi đánh máy.

python
from picamera2 import Picamera2

picam2 = Picamera2()
config = picam2.create_preview_configuration(
    main={"format": "RGB888", "size": (640, 480)}   # → BGR đúng cho OpenCV, 3 kênh
)
picam2.configure(config)
picam2.start()

frame = picam2.capture_array("main")
print(frame.shape)   # (480, 640, 3) — đúng thứ tự BGR, sẵn sàng cho cv2

05Vòng lặp thời gian thực — mẫu chuẩn cho AI pipeline

Đây là điểm khác biệt với 5 tài liệu gốc: thay vì chụp 1 ảnh tĩnh rồi thoát, một pipeline AI cần đọc liên tục frame theo thời gian thực.

python — realtime_loop.py
import time
from picamera2 import Picamera2

picam2 = Picamera2()
config = picam2.create_video_configuration(
    main={"format": "RGB888", "size": (640, 480)}
)
picam2.configure(config)
picam2.start()

try:
    frame_count = 0
    t_start = time.monotonic()
    while True:
        frame = picam2.capture_array("main")   # numpy array (480, 640, 3), BGR

        # ---- gọi model AI / xử lý ảnh ở đây ----
        # result = model.predict(frame)
        # -----------------------------------------

        frame_count += 1
        if frame_count % 60 == 0:
            fps = frame_count / (time.monotonic() - t_start)
            print(f"FPS trung bình: {fps:.1f}")
except KeyboardInterrupt:
    pass
finally:
    picam2.stop()
create_preview_configuration vs create_video_configuration vs create_still_configuration

preview: ưu tiên framerate, chất lượng vừa đủ — hợp cho vòng lặp AI thời gian thực. video: cân bằng, dùng khi cũng cần encode video song song. still: ưu tiên chất lượng tối đa (denoise mạnh hơn), framerate thấp hơn hẳn — không phù hợp cho vòng lặp liên tục, chỉ dùng khi chụp 1 ảnh chất lượng cao.

06Ví dụ: xử lý ảnh với OpenCV trong vòng lặp

Minh hoạ pattern chuẩn — dùng stream lores (độ phân giải thấp, xử lý nhanh) để phát hiện, và stream main (độ phân giải cao) để hiển thị/lưu kết quả. Đây là kỹ thuật dual-stream sẽ giải thích kỹ ở mục 7.

python — edge_detect_dualstream.py
import cv2
import numpy as np
from picamera2 import Picamera2

picam2 = Picamera2()
config = picam2.create_preview_configuration(
    main={"format": "RGB888", "size": (1280, 720)},   # độ phân giải cao — hiển thị/lưu
    lores={"format": "YUV420", "size": (320, 240)}     # độ phân giải thấp — xử lý nhanh
)
picam2.configure(config)
picam2.start()

try:
    while True:
        # Lấy kênh Y (grayscale) từ lores — nhanh, không cần convert màu
        lores = picam2.capture_array("lores")
        gray = lores[: config["lores"]["size"][1], : config["lores"]["size"][0]]

        edges = cv2.Canny(gray, 60, 140)
        edge_ratio = np.count_nonzero(edges) / edges.size

        if edge_ratio > 0.05:   # ngưỡng ví dụ — thay bằng logic model thật
            main = picam2.capture_array("main")
            cv2.imwrite("detected_frame.jpg", main)
            print(f"Phát hiện chuyển động/cạnh mạnh — edge_ratio={edge_ratio:.3f}")

except KeyboardInterrupt:
    pass
finally:
    picam2.stop()

Với kênh Y của YUV420, chỉ cần cắt đúng vùng width×height đầu tiên của buffer (planar format, kênh Y nằm trước) — không cần cv2.cvtColor nếu chỉ cần grayscale, tiết kiệm một bước xử lý mỗi frame.

07Hiệu năng: kỹ thuật dual-stream lores/main

Nguyên tắc chung khi ghép camera với AI: dùng ảnh nhỏ nhất, format nhẹ nhất có thể cho vòng lặp inference; chỉ lấy ảnh full-res khi thực sự cần lưu hoặc hiển thị.

Cấu hình (main / lores)FPS ghi nhận thực tế (RPi5)Ghi chú
XBGR8888 1640×1232 / YUV420 1640×1232~56 fpsKhông lưu file, chỉ đọc buffer liên tục
XBGR8888 640×480 / YUV420 640×480~83 fpsKhông lưu file

Số liệu tham khảo từ benchmark cộng đồng trên RPi5 — FPS thực tế phụ thuộc sensor, cấu hình, và có lưu/convert dữ liệu trong loop hay không. Luôn benchmark trên chính phần cứng của bạn.

Điểm khác biệt trên RPi5 (so với Pi4-)
Stream lores trên Pi 4 trở xuống bắt buộc phải là YUV420. Trên RPi5, lores có thể là format RGB — linh hoạt hơn, không cần convert YUV→RGB nếu model cần RGB trực tiếp, đổi lại băng thông cao hơn YUV420 (1.5 byte/pixel so với 3 byte/pixel của RGB888).
Quy tắc chọn format theo thứ tự ưu tiên tốc độ

YUV420 (1.5 byte/pixel, nhanh nhất) → RGB888 (3 byte/pixel, cân bằng, khớp OpenCV) → XRGB8888 (4 byte/pixel, chậm nhất, chỉ nên dùng nếu thư viện đích bắt buộc có kênh alpha).

08Zero-copy & tránh block với pre_callback

capture_array() copy dữ liệu ra khỏi buffer nội bộ. Với ảnh lớn hoặc FPS cao, copy liên tục có thể là điểm nghẽn. MappedArray cho phép truy cập buffer tại chỗ (in-place) mà không copy — hữu ích khi chỉ cần đọc/vẽ đè lên frame hiện có (ví dụ vẽ bounding box) trước khi nó được dùng cho việc khác (preview, encode).

python
from picamera2 import Picamera2, MappedArray
import cv2

picam2 = Picamera2()
picam2.configure(picam2.create_preview_configuration(
    main={"format": "RGB888", "size": (640, 480)}
))

def draw_overlay(request):
    # Chạy trên chính camera thread, ở tốc độ camera — không tạo thread riêng
    with MappedArray(request, "main") as m:
        cv2.putText(m.array, "AI đang xử lý...", (10, 30),
                    cv2.FONT_HERSHEY_SIMPLEX, 0.8, (0, 255, 0), 2)

picam2.pre_callback = draw_overlay
picam2.start(show_preview=True)

import time; time.sleep(30)
picam2.stop()
⚠️ pre_callback chạy trên camera thread

Hàm gán cho pre_callback chạy đồng bộ trên thread nội bộ của picamera2, ở đúng tốc độ camera. Model AI nặng (vài chục-trăm ms/frame) đặt trực tiếp ở đây sẽ làm nghẽn ngược lại tốc độ capture. Cách đúng: dùng pre_callback chỉ cho việc nhẹ (vẽ overlay, crop nhanh); còn inference nặng nên chạy ở thread/process riêng, nhận frame qua capture_array() trong vòng lặp chính như mục 5-6, và chấp nhận rớt frame (giống drop=true của appsink ở Phần 3) nếu model chậm hơn camera.

09libcamerify — khi cần giữ code OpenCV/V4L2 cũ

Nếu đã có sẵn code dùng cv2.VideoCapture(0) viết cho webcam USB và muốn chạy trên camera CSI RPi5 mà không sửa code, libcamerify (giới thiệu ở Phần 2) là lựa chọn nhanh hơn viết lại bằng picamera2 — đánh đổi lấy độ trễ cao hơn (~1-2s theo ghi nhận cộng đồng).

bash
sudo apt install libcamera-tools libcamera-v4l2
libcamerify python3 your_existing_opencv_script.py

Quy tắc chọn: code mới hoặc cần latency thấp → picamera2. Code cũ đã hoạt động tốt cho USB, chỉ cần "chạy được" trên CSI → libcamerify.

10Lộ trình tiếp theo: đến AI thật sự

picamera2 giải quyết vế "lấy frame". Vế "hiểu frame" (inference) là bước tiếp theo — vài hướng phổ biến trên RPi5:

TensorFlow Lite

Runtime inference nhẹ, model .tflite, hỗ trợ tốt trên ARM. Điểm khởi đầu phổ biến nhất cho object detection/classification trên RPi.

ONNX Runtime

Chạy model từ nhiều framework (PyTorch, TF) đã export sang .onnx. Linh hoạt nếu bạn train model bằng PyTorch.

Hardware AI accelerator (Hailo)

RPi5 có dòng phụ kiện tăng tốc AI dạng M.2/HAT chạy NPU Hailo, giảm tải CPU đáng kể cho inference thời gian thực. Kiểm tra tài liệu chính thức Raspberry Pi tại thời điểm mua vì dòng sản phẩm này cập nhật thường xuyên.

OpenCV DNN module

cv2.dnn nạp thẳng model ONNX/Caffe/TF mà không cần thêm dependency — hợp để thử nghiệm nhanh trước khi tối ưu bằng TFLite/Hailo.

Với riêng bối cảnh voice agent tiếng Việt trên RPi5

Nếu camera sẽ ghép chung với hệ thống nhận diện giọng nói/điều khiển phần cứng qua D-Bus đang xây dựng, pattern hợp lý là: vòng lặp picamera2 (mục 5) chạy trên 1 thread/process riêng, publish kết quả nhận diện (bounding box, class, v.v.) qua D-Bus signal xuống lớp action layer — cùng kiến trúc sdbus-cpp cho phần điều khiển phần cứng, giữ camera pipeline và voice pipeline tách biệt nhưng giao tiếp qua cùng một cơ chế IPC quen thuộc.

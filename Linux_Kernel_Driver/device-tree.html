Tài liệu tham khảo kỹ thuật

Linux Device Tree

Cách kernel Linux mô tả phần cứng trên các nền tảng không tự khám phá được thiết bị (ARM SoC, embedded Linux) — từ cú pháp DTS, cơ chế match driver, đến overlay và debug thực chiến.

root.dts
/dts-v1/;

/ {
	model = "Vendor Board Name";
	compatible = "vendor,board", "vendor,soc";
	#address-cells = <1>;
	#size-cells = <1>;

	/* moi node ben duoi la mot phan cua cay - than cay nay
	   chinh la thu ma kernel doc de biet "phan cung minh dang chay tren cai gi" */
};

01

Vì sao cần Device Tree

Trên PC, phần cứng phần lớn tự khai báo được: PCI liệt kê thiết bị qua config space, USB trả descriptor khi cắm vào, ACPI cấp sẵn bảng mô tả cho hệ điều hành. Kernel boot lên, dò bus, hỏi "anh là ai" và tự nhận diện.

Trên SoC nhúng (ARM và phần lớn nền tảng embedded Linux khác) thì không như vậy. Một loạt thiết bị nằm trên bus không tự khám phá được — chúng chỉ là các thanh ghi memory-mapped: UART ở địa chỉ này, SPI controller ở địa chỉ kia, GPIO controller có bấy nhiêu chân, ngắt số mấy, xung nhịp bao nhiêu. CPU không có cách nào "hỏi" phần cứng những thông tin đó; chỉ người thiết kế board mới biết.

Trước khi có Device Tree, thông tin này được hardcode thẳng vào C: mỗi board một file trong arch/arm/mach-*/board-*.c, gọi platform_device_register() tay cho từng thiết bị. Hệ quả: một kernel Image build cho board này không chạy được trên board khác dù cùng SoC, chỉ vì địa chỉ GPIO hay số ngắt lệch đi vài chỗ. Thêm board mới đồng nghĩa vá code, build lại, không có cách nào tách biệt.

Device Tree giải quyết đúng vấn đề đó bằng cách tách data ra khỏi code: driver chỉ chứa logic (cách nói chuyện với chip), còn "chip này nằm ở đâu, dùng ngắt nào, nối với GPIO nào" chuyển hết sang một cấu trúc dữ liệu mô tả riêng — cây Device Tree, biên dịch thành DTB (Device Tree Blob) và nạp cùng lúc với kernel lúc boot. Một kernel Image build một lần dùng chung được cho hàng chục board khác nhau, miễn là đổi đúng file .dtb.

Liên hệ với bus-device-driver model

Driver core của kernel (drivers/base) có một mô hình chung: mọi thiết bị là một struct device gắn vào một struct bus_type, và được ghép với struct device_driver phù hợp dựa trên vài tiêu chí khớp (id table, tên, hoặc compatible string). Với bus tự khám phá được (PCI, USB), device instance sinh ra từ chính phần cứng thật khi dò bus. Với platform bus — nơi hầu hết peripheral SoC trú ngụ — không có gì để "dò" cả, phải có ai đó khai báo device instance bằng tay. Ngày xưa việc đó nằm trong board file C; giờ đây Device Tree đảm nhiệm: kernel đọc DTB lúc boot, với mỗi node hợp lệ sinh ra một struct device tương ứng, rồi driver core tự match nó với driver đã đăng ký compatible khớp. Nói ngắn gọn: Device Tree chính là nguồn dữ liệu nạp cho vế "device" của mô hình bus-device-driver trên platform bus.

02

Cấu trúc & cú pháp DTS

File nguồn .dts là text, mô tả một cây: node gốc /, mỗi node có thể có node con, mỗi node mang theo các cặp property = value. Cây này biên dịch ra .dtb nhị phân — dạng duy nhất kernel thật sự đọc lúc chạy.

2.1Node

cú pháp node
nhan_node: ten-node@dia-chi {
	property-a = "gia tri";
	property-b = <1 2 3>;

	node-con@0 {
		/* ... */
	};
};
  • Label (nhan_node:) — tuỳ chọn, dùng để những nơi khác tham chiếu tới node này qua &nhan_node. Label không xuất hiện trong path thật của node.
  • Tên node — theo convention nên mô tả chức năng chứ không phải tên riêng của chip: serial, spi, ethernet, không phải uart0 hay my-device.
  • Unit-address — thường là địa chỉ thanh ghi dạng hex, không có tiền tố 0x. Dùng để phân biệt các node trùng tên (serial@101f0000, serial@101f2000), và phải khớp với giá trị đầu tiên trong property reg nếu node có reg — dtc sẽ cảnh báo nếu lệch.

2.2Kiểu giá trị property

DạngCú phápVí dụ
Rỗng (boolean)chỉ tên property, không có =interrupt-controller;
Chuỗi"..."compatible = "vendor,chip";
Danh sách chuỗi"...", "..."compatible = "vendor,chip-v2", "vendor,chip";

Phandle&label bên trong <> — dtc tự resolve thành sốinterrupt-parent = <&gic>;

2.3Property chuẩn hay gặp

PropertyÝ nghĩa
compatibleDanh sách chuỗi định danh — chìa khoá chính để driver core tìm driver phù hợp (xem mục 05).
modelChuỗi mô tả board/thiết bị cho người đọc, không dùng để matching.
status"okay" (bật), "disabled" (tồn tại nhưng không active). Pattern rất hay gặp: file .dtsi chung của SoC khai mọi peripheral với status = "disabled", board .dts chỉ bật lại đúng cái board thật có.
#address-cells / #size-cellsKhai trên node cha, quy định node con diễn giải reg của chính nó ra sao (xem mục 04, đây là phần hay gây rối nhất).
regĐịa chỉ + kích thước vùng nhớ mà node chiếm, theo đơn vị cells của node cha. Ý nghĩa cụ thể phụ thuộc bus (xem mục 06 cho SPI/I2C, nơi reg KHÔNG phải địa chỉ vật lý).

Ghi chú

Comment dùng đúng cú pháp C (// và /* */) vì file .dts thực sự chạy qua C preprocessor trước khi tới dtc — đây cũng là lý do #include, #define dùng được trong DTS dù nó không phải C thật (xem mục 03).

03

Toolchain: dts / dtsi / dtb / dtbo

3.1.dtsi và .dts — kế thừa theo tầng

.dtsi ("device tree include") mô tả những gì chung cho cả một SoC/family — mọi controller, mọi peripheral chip có, gần như luôn để status = "disabled" vì file này chưa biết board cụ thể nào sẽ dùng gì. File .dts của từng board #include file .dtsi đó, rồi override qua tham chiếu label để bật/cấu hình đúng phần board thật sự có:

board.dts
#include "soc-family.dtsi"

/ {
	model = "My Custom Board";
};

&spi0 {              /* tham chieu lai node da khai trong .dtsi qua label */
	status = "okay"; /* bat len - .dtsi da de san "disabled" */

	rfid@0 {          /* them node con moi - thiet bi gan ngoai that su co tren board nay */
		compatible = "vendor,rc522";
		reg = <0>;
	};
};

Đây không phải override toàn bộ node — mà là merge property vào đúng node đã tồn tại theo path/label, cực kỳ tiết kiệm: SoC vendor viết .dtsi một lần, hàng chục board khác nhau chỉ cần vài dòng .dts riêng.

3.2Vì sao #include/#define dùng được

.dts thật ra chạy qua cpp (C preprocessor) trước khi tới dtc. Đó là lý do các macro như GPIO_ACTIVE_LOW, IRQ_TYPE_EDGE_FALLING (định nghĩa trong include/dt-bindings/.../*.h) dùng được ngay trong DTS — chúng resolve thành số nguyên ngay ở bước preprocessor, dtc chỉ nhìn thấy con số cuối cùng, không biết gì về tên macro.

3.3dtc — Device Tree Compiler

bash
dtc -I dts -O dtb -o output.dtb input.dts       # bien dich dts -> dtb
dtc -I dtb -O dts -o decompiled.dts input.dtb   # dich nguoc de doi chieu/debug
dtc -@ -I dts -O dtb -o out.dtbo overlay.dts    # -@ : them __symbols__, bat buoc cho overlay

Khả năng dịch ngược (dtb → dts) rất quan trọng khi debug board thật: nó cho biết chính xác DTB nào đang chạy, có thể khác với source gốc nếu bootloader đã chỉnh sửa (fixup memory size, áp overlay...).

3.4Vị trí trong kernel source & build

Source nằm dưới arch/arm/boot/dts/<vendor>/ hoặc arch/arm64/boot/dts/<vendor>/, build bằng make dtbs (build tất cả) hoặc target riêng như make vendor/board.dtb. Trên các SoC dạng vendor BSP (kể cả Sigmastar) thường theo cùng cấu trúc này, chỉ khác đường dẫn vendor cụ thể tuỳ fork kernel.

3.5Bootloader nạp DTB thế nào

U-Boot thường chịu trách nhiệm: load .dtb vào RAM, rồi fdt addr $fdt_addr; bootm $kernel_addr - $fdt_addr (hoặc booti/bootz tuỳ arch). Địa chỉ DTB được truyền cho kernel qua thanh ghi (ARM 32-bit: r2) hoặc tham số boot protocol tương ứng. Kernel parse DTB rất sớm trong setup_arch() — trước khi bất kỳ driver nào chạy — để biết layout bộ nhớ, console, và toàn bộ cây thiết bị.

04

Address translation: #address-cells, #size-cells, reg, ranges

Đây là phần hay gây rối nhất với người mới — nhưng cơ chế thực ra rất máy móc một khi nắm được quy tắc: #address-cells/#size-cells khai trên node cha, quyết định node con phải diễn giải reg của chính nó ra sao.

4.1reg — số cell được cha quy định

Root node "/" trên nền 32-bit thường khai #address-cells = <1>; #size-cells = <1>; — nghĩa là reg của node con trực tiếp dưới "/" đọc theo từng cặp <địa-chỉ kích-thước>, mỗi phần 1 cell (1 u32). Nếu cha khai #address-cells = <2> (hay gặp trên bus cần không gian địa chỉ rộng hơn 32-bit, hoặc PCI cần thêm cell mã hoá bus/device/function), mỗi địa chỉ chiếm 2 cell: reg = <addr_hi addr_lo size_hi size_lo>;. Một property reg có thể chứa nhiều entry liên tiếp nếu node chiếm nhiều dải bộ nhớ rời nhau.

Ghi chú

Theo đặc tả, nếu một node không khai #address-cells/#size-cells, giá trị mặc định là 2 và 1. Trong thực tế hầu như mọi bus node đều khai tường minh — nhưng nếu quên khai trên một bus tự định nghĩa, đây chính là nguồn gốc của những giá trị reg bị đọc sai lệch khó hiểu.

4.2ranges — dịch địa chỉ qua bus lồng bus

Khi một node con là một bus khác (có không gian địa chỉ riêng, khác với bus cha), property ranges định nghĩa cách dịch một địa chỉ trong không gian con sang không gian cha:

  • ranges = <child-addr parent-addr length>; — child-addr dùng #address-cells của chính node này, parent-addr dùng #address-cells của node cha, length dùng #size-cells của chính node này.
  • ranges; rỗng (không giá trị) = ánh xạ 1:1 (identity mapping) — hay gặp trên "simple-bus", tức bus nội bộ đơn giản không dịch địa chỉ.
  • Không có property ranges nào cả = node đó không phải bus dịch được địa chỉ; các node con của nó không truy cập được bằng địa chỉ CPU thông thường.
vi dụ minh hoạ
/ {
	#address-cells = <1>;
	#size-cells = <1>;

	soc {
		compatible = "simple-bus";
		#address-cells = <1>;
		#size-cells = <1>;
		ranges = <0x0 0x3f000000 0x1000000>; /* con 0x0 -> cha 0x3f000000, dai 0x1000000 */

		spi0: spi@204000 {
			compatible = "vendor,spi";
			reg = <0x204000 0x1000>; /* dia chi trong khong gian con cua "soc" */
		};
	};
};

spi0 khai reg = <0x204000 ...> — đây là địa chỉ trong không gian địa chỉ của bus soc, không phải địa chỉ CPU thật. Vì soc có ranges ánh xạ 0x0 → 0x3f000000 cho một cửa sổ dài 0x1000000, và 0x204000 nằm trong cửa sổ đó, địa chỉ CPU thật sự là 0x3f000000 + 0x204000 = 0x3f204000. Driver không cần tự tính — of_address_to_resource()/platform_get_resource() làm việc dịch này ngầm, driver chỉ nhận địa chỉ CPU cuối cùng qua devm_ioremap_resource().

Thực chiến

Đây chính xác là kiểu cơ chế mà .dtsi của BCM283x (chip trên Raspberry Pi) dùng để ánh xạ "bus address" nội bộ sang địa chỉ CPU vật lý thật (khác nhau giữa Pi 3/4/5). Trên Raspberry Pi 5 của bạn, tự kiểm tra bằng dtc -I fs -O dts /sys/firmware/devicetree/base | grep -A2 ranges để xem giá trị ranges thật sự đang chạy — đáng tin hơn là nhớ số hex từ tài liệu.

05

Cơ chế kernel match Node → Driver

Kernel biểu diễn mỗi node DT trong bộ nhớ bằng struct device_node (dựng lúc boot khi parse DTB). Trên platform bus, mỗi node hợp lệ được bọc thành một struct platform_device. Việc "hợp lệ" ở đây chủ yếu do of_platform_populate()/of_platform_default_populate() quyết định — hàm này duyệt qua node con của cây DT chính (kernel tự gọi rất sớm lúc boot, driver hầu như không cần gọi tay trừ khi có bus con tự quản, ví dụ MFD driver populate node con của chính nó), với mỗi node con có compatible hợp lệ thì tạo một platform_device gắn vào platform bus.

5.1compatible string — chìa khoá matching

Driver đăng ký một bảng struct of_device_id[] gán qua .driver.of_match_table trong struct platform_driver. Driver core so khớp từng chuỗi trong property compatible của device (theo đúng thứ tự khai — cụ thể nhất trước) với bảng of_match_table đã đăng ký; driver nào có entry khớp thì thắng.

Ghi chú

Vì vậy nên liệt kê compatible từ cụ thể nhất (đúng chip đang dùng) đến tổng quát nhất (chip đời cũ tương thích): compatible = "vendor,chip-v2", "vendor,chip"; — nếu chưa có driver riêng cho chip-v2, kernel vẫn tận dụng được driver của chip đời trước nếu tương thích ngược.

5.2I2C và SPI — hơi khác platform bus

I2C/SPI không đi qua of_platform_populate(). Khi driver của chính controller (I2C adapter, SPI controller) gọi i2c_add_adapter()/spi_register_controller(), core của từng subsystem tự quét node con bên dưới node controller trong DT, tạo i2c_client/spi_device tương ứng cho mỗi node con có compatible hợp lệ. Driver của thiết bị con (như RC522) chỉ cần đăng ký spi_driver với of_match_table — không cần quan tâm cách "device" được sinh ra.

5.3device_get_match_data()

Hàm generic hiện đại lấy driver_data tương ứng với entry compatible đã match — dùng chung được cho cả DT lẫn ACPI, tiện khi driver cần chạy đa nền tảng. Rất hữu ích khi một driver support nhiều chip variant, mỗi compatible gắn kèm một cấu trúc cấu hình khác nhau; probe() chỉ cần một lệnh lấy đúng config theo đúng chip đã match, không cần chuỗi if/else so compatible thủ công.

Liên hệ với bus-device-driver model

Đây chính là bức tranh đầy đủ của mô hình bạn đang tìm hiểu: device_node (dữ liệu từ DTB) → platform_device/spi_device/i2c_client (vế "device") → driver core match với *_driver đã đăng ký compatible (vế "driver") → gọi probe(). Khác duy nhất so với model tổng quát là nguồn sinh ra "device" ở đây là DTB thay vì gọi *_device_register() hardcode trong C.

06

Bindings thường gặp

"Binding" là quy ước đặt tên property + ý nghĩa của nó cho một loại thiết bị/bus cụ thể, tài liệu hoá trong Documentation/devicetree/bindings/ (ngày nay phần lớn binding mới viết bằng YAML schema, kiểm tra tự động qua dt-schema/make dtbs_check). Dưới đây là các binding lõi hay chạm tới nhất khi làm SPI/GPIO/ngắt.

6.1GPIO

Node controller cần gpio-controller; (property rỗng, đánh dấu đây LÀ một GPIO controller) và #gpio-cells (số cell mỗi tham chiếu cần — hầu hết là 2: pin, flags). Bên tiêu thụ, property phải kết thúc bằng hậu tố -gpios (dạng cũ -gpio đã deprecated):

dts
reset-gpios = <&gpio 27 GPIO_ACTIVE_LOW>;

Lỗi thường gặp

GPIO_ACTIVE_LOW mô tả mức điện áp vật lý tương ứng với trạng thái "bật" theo datasheet — không phải giá trị driver truyền vào. Driver luôn gọi theo giá trị logic: gpiod_set_value(desc, 1) nghĩa là "bật", framework tự đảo mức điện áp thật dựa theo flag khai trong DT. Nhầm giữa hai khái niệm này là nguồn bug rất phổ biến khi mới chuyển từ code bare-metal (nơi bạn tự set mức điện áp tay) sang gpiod API.

6.2Interrupt

Node cấp ngắt cần interrupt-controller; (rỗng) và #interrupt-cells (số cell mỗi entry ngắt — GIC thường 3 cell [type, số ngắt, flags], một GPIO controller đóng vai trò interrupt controller thường dùng 2 cell [pin, kiểu trigger]). Bên tiêu thụ:

dts
interrupt-parent = <&gpio>;                         /* neu khong khai, ke thua tu node cha gan nhat */
interrupts = <25 IRQ_TYPE_EDGE_FALLING>;

6.3SPI

Lỗi thường gặp

Trên node dưới SPI controller, reg là chỉ số chip-select (0, 1, 2...) — không phải địa chỉ vật lý. Đây là điểm rất dễ nhầm vì trên bus khác (như platform bus ở mục 04) reg mang ý nghĩa hoàn toàn khác.

spi-max-frequency (Hz) gần như bắt buộc. Mode SPI (CPOL/CPHA) mặc định là mode 0 nếu không khai gì; cần mode khác thì thêm spi-cpha và/hoặc spi-cpol (cả hai đều là property rỗng — có mặt nghĩa là bật). Nếu chip-select không dùng chân CS cứng của controller mà dùng GPIO thường, khai cs-gpios trên chính node controller (không phải node thiết bị con), liệt kê theo thứ tự index.

6.4I2C

reg ở đây là địa chỉ slave 7-bit (hoặc 10-bit): reg = <0x50>; cho một EEPROM tại địa chỉ 0x50.

6.5Clock

clocks = <&clk-controller specifier...>; tham chiếu tới nguồn xung; clock-names = "tên1", "tên2"; đặt tên theo thứ tự tương ứng với clocks khi thiết bị cần nhiều input clock, để code driver gọi clk_get(dev, "tên") mà không cần nhớ thứ tự index.

6.6Pinctrl

pinctrl-names = "default", "sleep"; đặt tên các state, pinctrl-0/pinctrl-1 (index khớp vị trí trong pinctrl-names) trỏ tới nhóm pin tương ứng. State "default" thường được device core tự áp dụng ngầm lúc probe qua devm_pinctrl_get_select_default(), driver thường không cần gọi tay.

07

Đọc Device Tree trong driver

Mọi struct device sinh ra từ DT đều có sẵn con trỏ of_node (pdev->dev.of_node cho platform driver, spi->dev.of_node cho SPI driver...) — NULL nếu device không đến từ DT (board file cũ, ACPI), nên nếu code cần chạy đa nền tảng, luôn kiểm tra trước khi dùng.

7.1Đọc property cơ bản

c
int of_property_read_u32(const struct device_node *np, const char *propname, u32 *out_value);
int of_property_read_string(const struct device_node *np, const char *propname, const char **out);
bool of_property_read_bool(const struct device_node *np, const char *propname);
int of_property_read_u32_array(const struct device_node *np, const char *propname, u32 *out, size_t sz);

Các hàm of_property_read_* trả 0 nếu thành công, mã âm (-EINVAL, -ENODATA, -EOVERFLOW...) nếu thiếu property hoặc sai kiểu. Luôn kiểm tra giá trị trả về — đừng giả định property luôn tồn tại chỉ vì .dts của bạn có khai; driver có thể chạy trên board khác quên khai property đó. Riêng of_property_read_bool() không có khái niệm "lỗi" — nó chỉ trả true/false tuỳ property (dạng rỗng) có tồn tại hay không.

7.2GPIO — API hiện đại (gpiod)

c
/* property DT ten "reset-gpios" -> con_id chi can "reset", framework tu noi hau to */
struct gpio_desc *reset = devm_gpiod_get(&spi->dev, "reset", GPIOD_OUT_HIGH);
if (IS_ERR(reset))
	return PTR_ERR(reset);

gpiod_set_value_cansleep(reset, 1);   /* set theo GIA TRI LOGIC, framework tu dao cuc neu can */

con_id truyền vào không gồm hậu tố -gpios — framework tự nối. Flag như GPIOD_OUT_LOW/GPIOD_OUT_HIGH/GPIOD_IN cấu hình hướng chân ngay lúc lấy, không cần gọi thêm gpiod_direction_*(). API cũ hơn (of_get_named_gpio() + gpio_request() + gpio_direction_*()) vẫn có thể gặp trong code cũ nhưng không nên dùng cho code mới — gpiod là lớp trừu tượng cao hơn, hoạt động thống nhất bất kể nguồn gốc device là DT, board file hay ACPI.

7.3devm_* — resource tự dọn dẹp

Tiền tố devm_ (device-managed) nghĩa là kernel tự giải phóng resource khi device bị remove/unbind hoặc khi probe() thất bại giữa chừng — nên ưu tiên devm_* cho hầu hết resource (memory, gpio, irq, clk, regulator...) trong probe(), giảm hẳn bug quên free ở remove() hoặc trên các nhánh lỗi.

7.4Ngắt

c
int irq = platform_get_irq(pdev, 0);   /* platform driver: tu doc property "interrupts" */
if (irq < 0)
	return irq;
/* SPI driver: spi->irq da duoc core tu dien san neu node co khai "interrupts" */

platform_get_irq() trả về Linux IRQ number (số ảo đã map) sẵn sàng truyền cho request_irq()/devm_request_irq() — không phải số ngắt hardware ghi trong DT.

7.5Lấy driver data theo compatible đã match

c
const struct my_chip_config *cfg = device_get_match_data(&spi->dev);

Hữu ích khi một driver support nhiều chip variant, mỗi compatible string trong of_device_id[] gắn kèm một con trỏ .data khác nhau — probe() lấy đúng config theo đúng chip đã match, không cần so chuỗi thủ công.

08

Ví dụ hoàn chỉnh: driver SPI cho thiết bị kiểu RC522

Ghép lại toàn bộ cơ chế ở trên thành một ví dụ đầy đủ, dùng RC522 (RFID qua SPI) làm thiết bị mẫu — cùng loại bus bạn đã có kinh nghiệm thực tế. Đây là skeleton tập trung vào phần "đọc DT đúng cách", không phải driver RC522 hoàn chỉnh (giao thức thanh ghi MFRC522 nằm ngoài phạm vi tài liệu này).

8.1Mô tả trong DTS

rc522-overlay.dts (trích từ &spi0)
&spi0 {
	status = "okay";
	#address-cells = <1>;
	#size-cells = <0>;

	rc522: rfid@0 {
		compatible = "vendor,rc522";
		reg = <0>;                       /* chip-select index 0 - KHONG phai dia chi */
		spi-max-frequency = <1000000>;   /* RC522 toi da ~10MHz, an toan o 1MHz luc dau */
		/* khong khai spi-cpha/spi-cpol -> mac dinh mode 0, dung theo datasheet MFRC522 */

		interrupt-parent = <&gpio>;
		interrupts = <25 IRQ_TYPE_EDGE_FALLING>;   /* chan bao co tag RFID moi */
		reset-gpios = <&gpio 27 GPIO_ACTIVE_LOW>;  /* chan NRSTPD, active low theo datasheet */
	};
};

8.2Driver skeleton

rc522.c
#include <linux/module.h>
#include <linux/spi/spi.h>
#include <linux/gpio/consumer.h>
#include <linux/interrupt.h>
#include <linux/of.h>
#include <linux/delay.h>

struct rc522_priv {
	struct spi_device *spi;
	struct gpio_desc *reset_gpio;
	int irq;
};

static irqreturn_t rc522_irq_thread(int irq, void *data)
{
	struct rc522_priv *priv = data;

	/* TODO: doc FIFO qua SPI (spi_sync/spi_write_then_read), day du lieu the len userspace */
	dev_dbg(&priv->spi->dev, "phat hien tag moi\n");
	return IRQ_HANDLED;
}

static int rc522_probe(struct spi_device *spi)
{
	struct rc522_priv *priv;
	int ret;

	priv = devm_kzalloc(&spi->dev, sizeof(*priv), GFP_KERNEL);
	if (!priv)
		return -ENOMEM;

	priv->spi = spi;
	spi_set_drvdata(spi, priv);

	priv->reset_gpio = devm_gpiod_get(&spi->dev, "reset", GPIOD_OUT_HIGH);
	if (IS_ERR(priv->reset_gpio))
		return dev_err_probe(&spi->dev, PTR_ERR(priv->reset_gpio),
				     "khong lay duoc reset-gpios\n");

	/* xung reset theo datasheet: keo thap mot nhip roi tha ra */
	gpiod_set_value_cansleep(priv->reset_gpio, 0);
	usleep_range(100, 200);
	gpiod_set_value_cansleep(priv->reset_gpio, 1);

	priv->irq = spi->irq;   /* core da tu dien san tu property "interrupts" trong DT */
	if (priv->irq > 0) {
		ret = devm_request_threaded_irq(&spi->dev, priv->irq, NULL,
						rc522_irq_thread, IRQF_ONESHOT,
						"rc522", priv);
		if (ret)
			return dev_err_probe(&spi->dev, ret,
					     "khong dang ky duoc irq\n");
	}

	dev_info(&spi->dev, "RC522 san sang, CS=%d, IRQ=%d\n",
		 spi->chip_select, priv->irq);
	return 0;
}

static void rc522_remove(struct spi_device *spi)
{
	/* moi resource deu xin qua devm_* nen khong can tu don dep gi them o day */
}

static const struct of_device_id rc522_of_match[] = {
	{ .compatible = "vendor,rc522" },
	{ }
};
MODULE_DEVICE_TABLE(of, rc522_of_match);

static struct spi_driver rc522_driver = {
	.driver = {
		.name = "rc522",
		.of_match_table = rc522_of_match,
	},
	.probe = rc522_probe,
	.remove = rc522_remove,
};
module_spi_driver(rc522_driver);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Driver vi du: doc Device Tree cho RFID RC522 qua SPI");

Toàn bộ luồng: of_match_table khớp compatible → SPI core gọi rc522_probe() → driver đọc reset-gpios và interrupts thẳng từ of_node gắn sẵn trên spi->dev, không cần tự parse DTB — toàn bộ việc đó driver core đã làm trước khi probe() được gọi.

09

Device Tree Overlay

Overlay nạp thêm một phần cây DT vào lúc boot hoặc runtime mà không cần build lại/thay .dtb gốc — đúng nhu cầu khi thêm module mở rộng (HAT, cảm biến, mạch động cơ cắm thêm) mà base board không biết trước. Đây cũng là cơ chế chính Raspberry Pi dùng để bật thêm peripheral qua config.txt.

9.1Cú pháp fragment

Bắt đầu bằng /plugin/; (bên cạnh /dts-v1/;), nội dung chia thành các fragment@N, mỗi fragment trỏ tới một target (qua phandle hoặc path) và chèn nội dung vào bên trong __overlay__:

motor-pwm-overlay.dts
/dts-v1/;
/plugin/;

/ {
	compatible = "raspberrypi,5-model-b";

	fragment@0 {
		target = <&gpio>;
		__overlay__ {
			motor_pwm_pins: motor_pwm_pins {
				brcm,pins = <18>;
				brcm,function = <2>;   /* ALT5 = PWM0 tren chan GPIO18 */
			};
		};
	};

	fragment@1 {
		target = <&pwm>;
		__overlay__ {
			pinctrl-names = "default";
			pinctrl-0 = <&motor_pwm_pins>;
			status = "okay";
		};
	};
};

Sau khi overlay này được nạp, /sys/class/pwm/pwmchipN xuất hiện, sẵn sàng cho driver/consumer điều khiển motor set duty cycle qua sysfs hoặc qua pwm_get() trong kernel — bản thân overlay chỉ lo phần "bật controller + đúng pinmux", binding cụ thể cho driver động cơ/H-bridge thật (tuỳ IC bạn dùng cho voice agent) nằm ở lớp trên, tham chiếu tài liệu binding riêng của driver đó.

9.2Áp dụng trên Raspberry Pi

bash
# bien dich - co -@ de sinh __symbols__, bat buoc de resolve phandle luc ap overlay
dtc -@ -I dts -O dtb -o motor-pwm.dtbo motor-pwm-overlay.dts

# copy vao thu muc overlays (duong dan co the la /boot/overlays/ tuy ban Raspberry Pi OS)
sudo cp motor-pwm.dtbo /boot/firmware/overlays/

# them dong sau vao /boot/firmware/config.txt roi reboot
# dtoverlay=motor-pwm

Firmware Pi áp overlay vào DTB trước khi kernel boot — không phải kernel tự làm việc này.

9.3Áp dụng runtime qua configfs (không cần reboot)

bash
sudo mkdir /sys/kernel/config/device-tree/overlays/motor-pwm
sudo cp motor-pwm.dtbo /sys/kernel/config/device-tree/overlays/motor-pwm/dtbo

Kernel apply ngay lập tức — rất hữu ích lúc phát triển overlay mới, tránh reboot liên tục. Cần kernel bật sẵn CONFIGFS_FS + OF_CONFIGFS (mặc định có trên Raspberry Pi OS).

10

Debug & công cụ

10.1Xem cây DT đang thật sự chạy

/proc/device-tree/ hoặc /sys/firmware/devicetree/base/ (tương đương, đường dẫn mới hơn) — mỗi property là một file nhỏ chứa raw bytes. Dùng để xác nhận property thực tế kernel đang thấy, có thể khác source .dts gốc vì bootloader/firmware có thể đã chỉnh sửa (RPi firmware áp overlay, U-Boot fixup kích thước RAM...).

bash
# dich nguoc truc tiep tu cay dang chay (-I fs: doc tu filesystem, khong can file .dtb rieng)
dtc -I fs -O dts -o running.dts /sys/firmware/devicetree/base

# tim loi lien quan parse/match DT
dmesg | grep -iE "of_|devicetree|fdt"

10.2Lỗi cú pháp/logic thường gặp

Lỗi hay gặp nhất với người mới

Quên set lại status = "okay"; sau khi override một node vốn "disabled" sẵn trong .dtsi chung của SoC. Hậu quả: device không bao giờ được tạo ra — không có lỗi, không có warning nào cả, driver đơn giản không probe(). Rất dễ khiến người mới đi tìm bug trong driver cả buổi trong khi vấn đề chỉ nằm ở một dòng status thiếu trong .dts.

  • Quên #size-cells trên một bus node tự định nghĩa → reg của node con bị đọc sai số cell, hoặc dtc báo lỗi biên dịch.
  • unit-address không khớp giá trị đầu tiên trong reg (VD node tên spi@204000 nhưng reg = <0x205000 ...>;) → dtc cảnh báo "node name and first reg property differ".
  • Tham chiếu &label tới label không tồn tại (label ở node đã bị xoá, hoặc gõ sai tên) → dtc lỗi biên dịch "Reference to non-existent node".

0x00 — Mở đầu

Move, Copy & Vòng Đời Đối Tượng

Một con trỏ bị copy thay vì move. Một reference trỏ vào stack frame đã pop từ lâu. Một move constructor quên đánh dấu noexcept, khiến std::vector âm thầm copy toàn bộ buffer mỗi lần realloc thay vì move. Đây không phải lỗi cú pháp — code vẫn biên dịch sạch, vẫn chạy được trên desktop, vẫn pass code review.

Chúng chỉ lộ ra khi buffer DMA 4KB bị double-free lúc 3 giờ sáng, hoặc khi firmware chạy ổn định trên máy dev nhưng crash ngẫu nhiên trên target RAM giới hạn. Tài liệu này đi sâu vào phần C++ hay bị hiểu sai nhất: điều gì thực sự xảy ra trong vùng nhớ khi một đối tượng được copy, được move, và kết thúc vòng đời — cùng với những hệ quả rất cụ thể của nó trong lập trình embedded.

Copy nhân đôi dữ liệu trong vùng nhớ · Move chỉ chuyển quyền sở hữu địa chỉ

Phạm vi tài liệu: value categories, copy/move semantics, Rule of Zero/Three/Five, copy elision, perfect forwarding, storage duration & lifetime, các lỗi vùng nhớ thường gặp, và những cân nhắc đặc thù khi viết C++ cho bare-metal / embedded Linux — nơi mỗi allocation, mỗi memcpy đều có giá.

0x01

Value Categories

Toàn bộ overload resolution giữa copy constructor và move constructor — tức là compiler quyết định "chỗ này nên copy hay move" — dựa trên value category của biểu thức, không dựa trên kiểu dữ liệu. Đây là nền tảng bắt buộc phải nắm trước khi đọc các phần sau.

C++11 phân loại mọi biểu thức theo hai thuộc tính độc lập: có identity hay không (lấy địa chỉ được, tham chiếu lại được nhiều lần) và có thể move hay không (được phép "cướp" tài nguyên bên trong). Tổ hợp hai thuộc tính đó cho ra 3 category thực sự cần nhớ:

CategoryIdentityMovableVí dụ điển hình
lvalue✅❌x, *p, arr[i], hàm trả T&
prvalue❌✅42, x + 1, temporary, hàm trả T
xvalue✅✅std::move(x), hàm trả T&&

glvalue (lvalue ∪ xvalue — nhóm "có identity") và rvalue (prvalue ∪ xvalue — nhóm "có thể move") chỉ là hai tên gọi chung cho tiện nói chuyện; cái cần nhớ thật sự là 3 dòng trong bảng trên.

Đặt được & trước biểu thức mà vẫn biên dịch → glvalue (lvalue/xvalue). Biểu thức có thể "chảy" thẳng vào move constructor mà không cần ép kiểu tường minh → rvalue (prvalue/xvalue). String literal là trường hợp ngoại lệ đáng nhớ: nó là lvalue kiểu mảng, chỉ decay thành con trỏ (prvalue) khi ngữ cảnh yêu cầu.

0x02

Copy Semantics

COPY

Copy constructor (T(const T&)) và copy assignment (T& operator=(const T&)) tạo ra một bản sao độc lập hoàn toàn — sau khi copy, hai đối tượng không còn liên hệ gì với nhau về vùng nhớ. Copy xảy ra ở nhiều chỗ dễ bị bỏ sót: truyền tham số theo giá trị, trả về theo giá trị (khi không được elide), push_back/insert vào container, gán thông thường.

Shallow copy vs Deep copy

Nếu class có raw pointer member và không tự viết copy constructor, compiler sinh ra bản memberwise copy — tức shallow copy: con trỏ được copy nguyên giá trị địa chỉ, không copy nội dung nó trỏ tới. Hai đối tượng cùng trỏ vào một vùng heap. Khi cả hai bị hủy, delete/delete[] được gọi hai lần trên cùng một địa chỉ.

C++ UB — double free
class Buffer {
public:
    explicit Buffer(size_t size) : size_(size), data_(new uint8_t[size]) {}
    ~Buffer() { delete[] data_; }
    // Không viết copy ctor/assign -> compiler tự sinh bản memberwise (SHALLOW!)
private:
    size_t size_;
    uint8_t* data_;
};

void process(Buffer b) { /* ... */ }        // nhận theo giá trị -> 1 shallow copy

int main() {
    Buffer a(1024);
    Buffer b = a;                            // shallow copy: b.data_ == a.data_
    process(a);                              // thêm 1 shallow copy nữa
}   // a, b và bản copy trong process() cùng "sở hữu" MỘT con trỏ
    // -> delete[] được gọi nhiều lần trên cùng địa chỉ -> heap corruption

Bản deep copy đúng phải tự cấp phát vùng nhớ mới và sao chép nội dung:

C++ COPY
Buffer(const Buffer& other)
    : size_(other.size_), data_(new uint8_t[other.size_]) {
    std::memcpy(data_, other.data_, size_);
}

Buffer& operator=(const Buffer& other) {
    if (this == &other) return *this;   // guard tự-gán
    // allocate TRƯỚC khi đổi state -> an toàn nếu new ném exception
    auto* new_data = new uint8_t[other.size_];
    std::memcpy(new_data, other.data_, other.size_);
    delete[] data_;
    data_ = new_data;
    size_ = other.size_;
    return *this;
}
Idiom đáng biết — Copy-and-swap

Viết một hàm swap không ném exception, rồi để operator= nhận tham số theo giá trị và swap với *this. Compiler tự chọn copy hoặc move constructor cho tham số tùy value category của đối số — một hàm gán xử lý được cả hai trường hợp, exception-safe, không lặp logic:

friend void swap(Buffer& a, Buffer& b) noexcept {
    using std::swap;
    swap(a.size_, b.size_);
    swap(a.data_, b.data_);
}
Buffer& operator=(Buffer other) {   // copy hoặc move tùy caller
    swap(*this, other);
    return *this;
}                                    // other (bản cũ) bị hủy khi ra khỏi scope

0x03

Move Semantics

MOVE

Rvalue reference (T&&) là kiểu tham chiếu chỉ bind được vào rvalue (prvalue/xvalue) — tức những biểu thức compiler biết chắc "sắp hết dùng", nên cho phép hàm nhận nó lấy luôn tài nguyên bên trong thay vì copy. Move constructor (T(T&& other)) và move assignment (T& operator=(T&& other)) khai thác đúng điều đó.

std::move không di chuyển gì cả

std::move chỉ là một static_cast ép biểu thức thành xvalue, để overload resolution chọn nhánh move thay vì copy. Bản thân nó không di chuyển byte nào:

template <typename T>
constexpr std::remove_reference_t<T>&& move(T&& t) noexcept {
    return static_cast<std::remove_reference_t<T>&&>(t);
}
C++ MOVE
Buffer(Buffer&& other) noexcept
    : size_(other.size_), data_(other.data_) {
    other.data_ = nullptr;    // "cướp" xong PHẢI để other ở trạng thái an toàn để hủy
    other.size_ = 0;
}

Buffer& operator=(Buffer&& other) noexcept {
    if (this == &other) return *this;     // guard tự-move-gán
    delete[] data_;
    data_ = other.data_;
    size_ = other.size_;
    other.data_ = nullptr;
    other.size_ = 0;
    return *this;
}

Trạng thái "moved-from" nghĩa là gì?

Chuẩn C++ chỉ đảm bảo các kiểu trong thư viện chuẩn, sau khi bị move khỏi, ở trạng thái "valid but unspecified": object vẫn hợp lệ để gán mới hoặc hủy, nhưng giá trị bên trong không xác định — không được đọc/dùng tiếp. Với kiểu tự viết, bạn quyết định trạng thái đó là gì; quy ước phổ biến là null hóa con trỏ, reset size về 0, để move-from object trở nên vô hại khi bị destructor gọi.

noexcept — chi tiết nhỏ quyết định hiệu năng lớn

std::vector (và các container khác) khi realloc phải chọn: move hay copy từng phần tử cũ sang vùng nhớ mới? Để giữ strong exception guarantee, container chỉ dùng move nếu move constructor được đánh dấu noexcept (hoặc class không có copy ctor khả dụng) — cơ chế này gọi là std::move_if_noexcept. Quên noexcept không gây lỗi biên dịch, chỉ âm thầm khiến container copy thay vì move.

C++
std::vector<Buffer> v;
v.reserve(1);
v.emplace_back(1024);
v.emplace_back(1024);   // size == capacity -> vector phải realloc

// Nếu Buffer(Buffer&&) KHÔNG noexcept nhưng Buffer(const Buffer&) tồn tại:
//   -> move_if_noexcept chọn COPY từng phần tử cũ sang buffer mới
//   -> biên dịch sạch, không warning mặc định, chỉ chậm hơn + tốn allocation
// Bật -Wall kèm clang-tidy performance-noexcept-move-constructor để bắt lỗi này.
Luôn đánh dấu noexcept khi có thể

Move constructor/assignment nên noexcept bất cứ khi nào việc move thật sự không thể ném exception (gần như luôn đúng với các thao tác chỉ copy con trỏ/số nguyên). Đây là một trong những chi tiết dễ quên nhất và ảnh hưởng trực tiếp đến hiệu năng realloc của container trên hệ thống nhạy cảm về thời gian thực.

0x04

Rule of Zero / Three / Five

Rule of Three (trước C++11): nếu class cần tự viết một trong ba — destructor, copy constructor, copy assignment — gần như chắc chắn cần viết cả ba, vì đó là dấu hiệu class đang tự quản lý một resource thủ công. Rule of Five (C++11+) mở rộng thêm move constructor và move assignment. Rule of Zero — thực hành được khuyến nghị nhất — là đừng viết bất kỳ cái nào trong năm cái đó; hãy compose class từ những member đã tự quản lý đúng resource của chúng (RAII members).

Bảng sinh ngầm định của compiler

Việc bạn khai báo một trong năm special member function ảnh hưởng đến việc compiler có tự sinh những cái còn lại hay không, theo quy tắc khá rối và hay bị nhớ sai:

Bạn khai báoDefault CtorCopy CtorCopy AssignMove CtorMove Assign
Không gì cả✅✅✅✅✅
Ctor có tham số➖✅✅✅✅
Destructor✅⚠️⚠️➖➖
Copy Ctor➖👤⚠️➖➖

Bẫy kinh điển — silent fallback to copy

Class chỉ viết destructor (cực kỳ phổ biến với class quản lý resource) khiến move ctor/assign không được sinh, nhưng copy ctor/assign vẫn còn (dù deprecated). std::move(obj) hay std::vector realloc lúc này vẫn biên dịch được — chỉ là chúng âm thầm gọi copy thay vì move. Nếu copy ctor cũng là bản mặc định (shallow), đây chính là con đường ngắn nhất dẫn đến double-free.

Rule of Zero trong thực tế

Thay vì viết tay cả năm hàm, hãy để mỗi resource được sở hữu bởi đúng một RAII member, rồi để compiler tự sinh move/copy bằng cách move/copy từng member. Ví dụ một buffer DMA cần quản lý cả vùng nhớ heap lẫn một DMA channel handle:

C++ Rule of Zero
// RAII wrapper cho DMA channel - đối tượng DUY NHẤT sở hữu resource này
class DmaChannel {
public:
    DmaChannel() : id_(dma_acquire_channel()) {}
    ~DmaChannel() { if (id_ >= 0) dma_release_channel(id_); }

    DmaChannel(const DmaChannel&) = delete;             // không cho copy handle
    DmaChannel& operator=(const DmaChannel&) = delete;

    DmaChannel(DmaChannel&& other) noexcept : id_(other.id_) {
        other.id_ = -1;
    }
    DmaChannel& operator=(DmaChannel&& other) noexcept {
        if (this != &other) {
            if (id_ >= 0) dma_release_channel(id_);
            id_ = other.id_;
            other.id_ = -1;
        }
        return *this;
    }

    int id() const { return id_; }
private:
    int id_;
};

// DmaBuffer chỉ COMPOSE - đây mới thực sự là Rule of Zero
class DmaBuffer {
public:
    explicit DmaBuffer(size_t size)
        : data_(std::make_unique<uint8_t[]>(size)), size_(size) {}

    // Không viết destructor, copy, move nào cả:
    //  - unique_ptr<uint8_t[]> tự quản lý vùng heap
    //  - DmaChannel tự quản lý DMA channel
    //  - compiler sinh move ctor/assign ĐÚNG bằng cách move từng member
    //  - compiler XÓA copy ctor/assign vì cả hai member đều non-copyable
    //    -> cố tình copy DmaBuffer là LỖI BIÊN DỊCH, không có double-free ẩn

    uint8_t* data() const { return data_.get(); }
    size_t size() const { return size_; }
private:
    std::unique_ptr<uint8_t[]> data_;
    size_t size_;
    DmaChannel channel_;
};

Khi bắt buộc phải khai báo một trong năm hàm (ví dụ để cấm copy tường minh), ưu tiên cú pháp = default / = delete thay vì viết thân hàm tay — thể hiện rõ chủ đích, không tự phát sinh logic dư thừa:

C++
class NonCopyableHandle {
public:
    NonCopyableHandle() = default;
    NonCopyableHandle(const NonCopyableHandle&) = delete;
    NonCopyableHandle& operator=(const NonCopyableHandle&) = delete;
    NonCopyableHandle(NonCopyableHandle&&) = default;
    NonCopyableHandle& operator=(NonCopyableHandle&&) = default;
    ~NonCopyableHandle() = default;
};
0x05

Copy Elision & RVO / NRVO

RVO (Return Value Optimization) — khi hàm trả về một prvalue — cho phép compiler dựng object trực tiếp vào vùng nhớ của caller, bỏ qua hoàn toàn copy/move. NRVO (Named RVO) là biến thể áp dụng cho biến cục bộ có tên được return, và không được chuẩn C++ đảm bảo — dù hầu hết compiler hiện đại đều làm được trong các trường hợp đơn giản.

C++
DmaBuffer make_buffer(size_t n) {
    return DmaBuffer(n);   // RVO trên prvalue - C++17: GUARANTEED, 0 lời gọi copy/move
}

DmaBuffer make_buffer_named(size_t n) {
    DmaBuffer buf(n);
    // ... xử lý buf ...
    return buf;   // NRVO - hầu hết compiler làm được, nhưng không được chuẩn đảm bảo
}
Anti-pattern — return std::move(local)

Viết std::move quanh biến cục bộ trong câu lệnh return thường làm mọi thứ tệ hơn, không phải tốt hơn: nó phá khả năng NRVO (vì compiler không còn thấy đây là "trả về thẳng một biến có tên" theo đúng mẫu để elide), ép phải gọi move constructor thay vì loại bỏ hoàn toàn lệnh gọi. -Wpessimizing-move (GCC/Clang) cảnh báo chính xác trường hợp này.

DmaBuffer make_buffer_bad(size_t n) {
    DmaBuffer buf(n);
    return std::move(buf);   // ❌ phá NRVO, ép move thay vì 0 lời gọi nào cả
}

Since C++11, biến cục bộ đứng một mình trong return đã tự động được coi như rvalue cho mục đích overload resolution nếu NRVO không áp dụng được — nghĩa là viết std::move thủ công ở đây gần như luôn thừa, và có thể khiến tình huống elide-được biến thành move-bắt-buộc.

C++17: copy elision không còn là "optimization"

Từ C++17, với prvalue, đây không còn là một hành vi được phép bỏ qua nữa — ngôn ngữ định nghĩa lại rằng prvalue chưa "materialize" thành object cho tới khi thật sự cần. Hệ quả: copy/move constructor thậm chí không cần tồn tại để đoạn code sau biên dịch được: C++17

C++
struct NoisyBuffer {
    explicit NoisyBuffer(size_t) { std::puts("constructed"); }
    NoisyBuffer(const NoisyBuffer&) = delete;   // XÓA cả copy ctor
    NoisyBuffer(NoisyBuffer&&) = delete;        // lẫn move ctor
};

NoisyBuffer make() {
    // Vẫn biên dịch! prvalue "materialize" thẳng vào storage của caller -
    // không có ctor copy/move nào được gọi.
    return NoisyBuffer(1024);
}

Lưu ý phân biệt: quy tắc guaranteed elision ở trên chỉ áp dụng cho prvalue. NRVO (trả về biến có tên) vẫn chỉ là optimization được cho phép, không bắt buộc, và vẫn đòi hỏi move hoặc copy constructor phải tồn tại (kể cả khi cuối cùng không được gọi tới).

0x06

Perfect Forwarding

T&& mang hai ý nghĩa hoàn toàn khác nhau tùy ngữ cảnh. Trong một hàm template mà T được deduce từ đối số, T&& là forwarding reference (hay "universal reference") — bind được vào cả lvalue lẫn rvalue. Trong mọi ngữ cảnh khác (kiểu cụ thể, không deduce), T&& là rvalue reference thật sự — chỉ bind vào rvalue.

C++
template <typename T>
void wrapper(T&& arg) {              // forwarding reference: T được deduce
    inner(std::forward<T>(arg));      // giữ nguyên value category gốc của arg
}

void concrete(DmaBuffer&& arg);      // rvalue reference THẬT: T=DmaBuffer, không deduce

Cơ chế đứng sau là reference collapsing: khi deduction tạo ra tham chiếu-tới-tham-chiếu, chỉ tổ hợp && && mới collapse thành &&; mọi tổ hợp còn lại collapse về &:

Khai báo (T là T&)Kết quả sau collapsing
T& &T&
T& &&T&
T&& &T&
T&& &&T&&

std::forward<T>(arg) dùng chính kết quả deduce của T để "phát lại" đúng value category caller đã truyền vào — lvalue vẫn ra lvalue, rvalue vẫn ra rvalue. Đây là khối xây dựng tiêu chuẩn cho các hàm factory nhận số lượng tham số bất kỳ:

C++
template <typename T, typename... Args>
std::unique_ptr<T> make_unique_custom(Args&&... args) {
    return std::unique_ptr<T>(new T(std::forward<Args>(args)...));
}
Lỗi thường gặp — dùng std::move thay vì std::forward

std::move bên trong một forwarding function luôn ép đối số thành rvalue, bất kể caller truyền lvalue hay rvalue. Nếu caller còn dùng biến đó sau lời gọi, họ sẽ đọc phải trạng thái moved-from ngoài ý muốn — một bug im lặng, khó phát hiện qua review thông thường.

template <typename T>
void log_and_forward(T&& arg) {
    log(arg);
    inner(std::move(arg));         // ❌ luôn ép rvalue, kể cả khi arg vốn là lvalue
    // Đúng:  inner(std::forward<T>(arg));
}

Object Lifetime & Storage Duration

C++ định nghĩa 4 storage duration: automatic (biến local, gắn với scope), dynamic (heap, qua new/delete hoặc smart pointer), static (biến global, static local, static member — sống suốt vòng đời chương trình), và thread-local (C++11 — mỗi thread một bản riêng, sống hết vòng đời thread đó).

Mô hình minh họa phổ biến (kiểu Unix process) — trên MCU bare-metal, layout thật do linker script (.ld) quyết định và có thể khác đáng kể

Static initialization order fiasco

Thứ tự khởi tạo static object trong cùng một file luôn đúng theo thứ tự khai báo. Nhưng thứ tự khởi tạo giữa các translation unit khác nhau là không xác định. Nếu static object ở file A phụ thuộc vào static object ở file B, và B chưa được khởi tạo khi A chạy constructor — undefined behavior, thường biểu hiện thành giá trị rác im lặng.

C++ UB tiềm ẩn
// file_a.cpp
Logger g_logger;                    // static storage duration, global

// file_b.cpp
// ❌ nếu static init của file_b chạy TRƯỚC file_a -> g_logger CHƯA
//    được construct khi dùng -> hành vi không xác định
Config g_config(g_logger);

Giải pháp chuẩn là Meyer's Singleton: đưa static object vào bên trong một hàm, khởi tạo lazy ở lần gọi đầu tiên. Từ C++11, việc khởi tạo static local này được đảm bảo thread-safe ("magic statics") — cùng cơ chế Singleton pattern, áp dụng đúng chỗ để giải quyết vấn đề thứ tự khởi tạo:

C++ C++11
Logger& logger() {
    static Logger instance;   // khởi tạo ở lần gọi ĐẦU TIÊN, thread-safe, thứ tự luôn đúng
    return instance;
}

Lifetime extension của temporary

Bind một temporary trực tiếp vào const T& hoặc T&& sẽ kéo dài lifetime của temporary đó bằng đúng lifetime của reference. Nhưng quy tắc này không lan truyền qua return hay qua member — hai nguồn dangling reference phổ biến nhất:

C++ UB — dangling
const std::string& r = std::string("hello");   // OK: lifetime được kéo dài bằng r

const std::string& get_name() {
    return std::string("temp");    // ❌ dangling ngay - extension KHÔNG áp dụng qua return
}

struct Holder {
    const std::string& ref;
    Holder(const std::string& s) : ref(s) {}   // nếu s là temporary -> ref dangling
};                                                // ngay khi constructor kết thúc

std::string_view sv = std::string("hello") + " world";
// ❌ std::string tạm bị hủy cuối statement -> sv dangling trước cả khi dùng lần đầu

Lỗi thường gặp về Vùng nhớ & Vòng đời

Use-after-move

Dùng object như thể nó vẫn còn giá trị cũ sau khi đã bị move khỏi. Với kiểu tự viết, nếu move constructor null hóa con trỏ, đọc/ghi lại con trỏ đó sau move là null dereference:

C++ UB
DmaBuffer buf(1024);
auto buf2 = std::move(buf);
buf.data()[0] = 0xFF;   // ❌ buf.data() == nullptr sau move -> null dereference
                          // "buf" không còn đại diện cho buffer 1024 byte nữa

Self-move-assignment

Thiếu guard tự-gán trong move assignment khiến a = std::move(a) giải phóng chính vùng nhớ nó sắp đọc từ đó — lỗi hiếm gặp trực tiếp nhưng dễ xảy ra gián tiếp qua code generic (template, thuật toán tự viết thao tác trên container):

C++ UB
DmaBuffer& operator=(DmaBuffer&& other) noexcept {
    // ❌ THIẾU: if (this == &other) return *this;
    delete[] data_;          // this == &other -> đang giải phóng vùng nhớ CỦA CHÍNH other
    data_ = other.data_;     // other.data_ giờ đã dangling - gán lại con trỏ vừa delete
    ...
}

Object slicing

Truyền một object đa hình theo giá trị vào tham số kiểu base class sẽ cắt bỏ hoàn toàn phần derived — kể cả vtable pointer. Không lỗi biên dịch, không warning mặc định, chỉ đơn giản là đa hình ngừng hoạt động:

C++ Slicing
class Sensor { public: virtual void read(); };
class TemperatureSensor : public Sensor {
public:
    void read() override;
private:
    float calibration_offset_;
};

void process(Sensor s) { s.read(); }   // ❌ nhận theo GIÁ TRỊ

TemperatureSensor ts;
process(ts);   // "slicing": phần TemperatureSensor (kể cả vtable) bị cắt bỏ
                // s.read() gọi Sensor::read() - KHÔNG gọi bản override, im lặng.

// Sửa: nhận theo reference hoặc pointer để giữ đa hình
void process(Sensor& s) { s.read(); }   // ✅
void process(Sensor* s)  { s->read(); }  // ✅

Iterator / reference invalidation sau realloc

Khi container phải realloc, toàn bộ phần tử cũ được move (hoặc copy) sang vùng nhớ mới rồi vùng cũ bị giải phóng — mọi iterator, pointer, reference trỏ vào phần tử cũ lập tức dangling. Đây là hệ quả trực tiếp của cách move semantics vận hành bên trong container:

C++ UB
std::vector<DmaBuffer> buffers;
buffers.reserve(1);
buffers.emplace_back(64);
DmaBuffer& ref = buffers[0];    // reference vào phần tử đầu

buffers.emplace_back(64);        // vượt capacity -> realloc -> TOÀN BỘ phần tử cũ bị
                                   // move sang vùng nhớ mới, vùng cũ giải phóng
ref.data()[0] = 0xFF;            // ❌ ref trỏ vào vùng nhớ ĐÃ GIẢI PHÓNG - UB
Ghi chú

reserve() đủ dung lượng trước, hoặc dùng std::deque/danh sách chỉ mục thay vì giữ reference/pointer sống qua các lần push_back/emplace_back không kiểm soát được capacity.

Cân nhắc cho Embedded Systems

Move khi không có heap

Move thật sự hữu ích khi có một con trỏ/handle để "cướp" thay vì phải copy dữ liệu. Với container dung lượng cố định như etl::vector<T,N> hay std::array<T,N>, dữ liệu nằm inline ngay bên trong object — không có con trỏ heap nào để cướp, nên move vẫn phải chuyển từng phần tử. Nó chỉ rẻ hơn copy khi T tự nó tốn kém để copy, không rẻ hơn nếu T là kiểu trivial như uint8_t. Ngược lại, với các handle không thể nhân bản có ý nghĩa (DMA channel, file descriptor, GPIO đã claim) — move là cách duy nhất hợp lệ để chuyển quyền sở hữu:

C++
// Move KHÔNG rẻ hơn copy ở đây: dữ liệu inline, không có con trỏ heap để "cướp"
etl::vector<uint8_t, 256> a = build_frame();
etl::vector<uint8_t, 256> b = std::move(a);   // vẫn phải chuyển ~256 byte bên trong

// Move LÀ CÁCH DUY NHẤT hợp lệ ở đây: không thể "nhân bản" một DMA channel vật lý
DmaChannel ch  = acquire_channel();
DmaChannel ch2 = std::move(ch);

Placement new & quản lý lifetime thủ công

Trên static memory pool (không heap), object được construct trực tiếp vào một vùng nhớ đã cấp phát sẵn bằng placement new — và vì storage không "tự biết" nó đang chứa object gì, destructor phải được gọi tường minh:

C++
alignas(DmaBuffer) uint8_t storage[sizeof(DmaBuffer)];   // vùng nhớ tĩnh, không heap

DmaBuffer* buf = ::new (storage) DmaBuffer(1024);   // placement new: construct TẠI CHỖ
// ... dùng buf ...
std::destroy_at(buf);                                // C++17 - tương đương buf->~DmaBuffer()

Nếu tái sử dụng cùng một vùng storage cho một object mới (cùng kiểu, cùng địa chỉ), con trỏ cũ trỏ tới object cũ về mặt kỹ thuật đã hết hạn — cần std::launder để hợp thức hóa việc dùng lại: C++17

C++
DmaBuffer* p = ::new (storage) DmaBuffer(512);
std::destroy_at(p);
::new (storage) DmaBuffer(1024);   // object MỚI, cùng địa chỉ storage

// ❌ kỹ thuật là UB: p vẫn "trỏ" tới object cũ đã hết vòng đời
p->size();

auto* p2 = std::launder(p);   // ✅ hợp thức hóa việc dùng lại storage
p2->size();                    // OK

ISR & volatile

Copy/move constructor không atomic và không kèm memory barrier. Dữ liệu chia sẻ giữa ISR và main loop cần std::atomic hoặc critical section, không phải chỉ volatile — volatile chỉ ngăn compiler tối ưu bỏ việc đọc/ghi, không đảm bảo tính nguyên tử:

C++ Torn read
volatile SensorReading g_latest;   // ISR ghi, main loop đọc

void ISR_Handler() {
    g_latest = read_sensor();   // KHÔNG đảm bảo atomic nếu SensorReading > 1 word
}

SensorReading r = g_latest;   // main loop: có thể đọc trạng thái nửa-ghi (torn read)
Ghi chú C++20

Compound assignment (+=, ++...) trên biến volatile đã bị deprecate từ C++20 (P1152), chính vì nó ngầm gợi ý một sự "nguyên tử" mà ngôn ngữ chưa từng đảm bảo.

RAII cho peripheral: unique_ptr custom deleter hay tự viết?

C++
// Cách 1: unique_ptr + custom deleter - tận dụng RAII có sẵn, hợp khi handle LÀ con trỏ
struct GpioDeleter { void operator()(GpioHandle* h) const { gpio_release(h); } };
using GpioPtr = std::unique_ptr<GpioHandle, GpioDeleter>;

// Cách 2: RAII tự viết (như DmaChannel ở 0x04) - tự nhiên hơn khi handle KHÔNG phải
// con trỏ (int fd, int channel id) - không cần "giả vờ" nó là một con trỏ

Với stateless deleter, unique_ptr thường zero-overhead nhờ empty base optimization — chọn cách nào chủ yếu là vấn đề handle có tự nhiên biểu diễn như con trỏ hay không, không phải vấn đề hiệu năng.

Ví dụ đầy đủ

Gộp lại toàn bộ: Rule of Zero, move-only API, guaranteed elision, và copy bị chặn ngay từ lúc biên dịch — một driver quản lý hàng đợi buffer DMA:

C++ Rule of Zero
#include <cstdint>
#include <cstddef>
#include <memory>
#include <vector>
#include <utility>

// --- Giả lập API phần cứng ---
int  dma_acquire_channel();
void dma_release_channel(int id);

// --- RAII wrapper cho DMA channel ---
class DmaChannel {
public:
    DmaChannel() : id_(dma_acquire_channel()) {}
    ~DmaChannel() { if (id_ >= 0) dma_release_channel(id_); }

    DmaChannel(const DmaChannel&) = delete;
    DmaChannel& operator=(const DmaChannel&) = delete;

    DmaChannel(DmaChannel&& other) noexcept : id_(other.id_) { other.id_ = -1; }
    DmaChannel& operator=(DmaChannel&& other) noexcept {
        if (this != &other) {
            if (id_ >= 0) dma_release_channel(id_);
            id_ = other.id_;
            other.id_ = -1;
        }
        return *this;
    }
    int id() const { return id_; }
private:
    int id_;
};

// --- Buffer DMA - Rule of Zero, compose từ 2 RAII member ---
class DmaBuffer {
public:
    explicit DmaBuffer(size_t size)
        : data_(std::make_unique<uint8_t[]>(size)), size_(size) {}

    uint8_t*       data()       { return data_.get(); }
    const uint8_t* data() const { return data_.get(); }
    size_t         size() const { return size_; }
    int            channel_id() const { return channel_.id(); }
private:
    std::unique_ptr<uint8_t[]> data_;
    size_t size_;
    DmaChannel channel_;
};

// --- Driver: chỉ nhận buffer qua move, không bao giờ qua copy ---
class DmaQueue {
public:
    void submit(DmaBuffer&& buf) {           // chỉ nhận rvalue - buộc caller thể hiện
        pending_.push_back(std::move(buf));   // rõ ý định "giao hẳn quyền sở hữu"
    }
    size_t pending_count() const { return pending_.size(); }
private:
    std::vector<DmaBuffer> pending_;
};

int main() {
    DmaQueue queue;

    DmaBuffer a(1024);
    // DmaBuffer b = a;   // ❌ LỖI BIÊN DỊCH: copy ctor = deleted (đúng như ý muốn)

    queue.submit(std::move(a));   // ✅ move: chuyển buffer + DMA channel cho queue
    // a.data() giờ là nullptr - "a" đã hết vai trò, không nên dùng tiếp

    queue.submit(DmaBuffer(512));   // ✅ prvalue - elision rồi move vào vector
    return 0;
}
Vì sao submit() nhận T&& thay vì T

Chữ ký submit(DmaBuffer&& buf) từ chối lvalue hoàn toàn trừ khi caller viết std::move(...) tường minh — buộc ý định "giao hẳn quyền sở hữu" phải hiện rõ tại nơi gọi, thay vì để trình biên dịch âm thầm chọn hộ như khi tham số nhận theo giá trị.

Cheat Sheet

Checklist khi viết một class sở hữu resource

  • 01Ưu tiên Rule of Zero trước — compose từ RAII member (unique_ptr, vector, string, container ETL...) thay vì tự quản lý resource thủ công.
  • 02Nếu bắt buộc quản lý resource thủ công: viết đủ cả năm hàm, hoặc = delete tường minh những gì không cho phép.
  • 03Move ctor/assign luôn đánh dấu noexcept khi thao tác bên trong thật sự không thể ném exception.
  • 04Guard tự-gán (this != &other) trong cả copy assignment lẫn move assignment.
  • 05Sau khi move-from, để object ở trạng thái an toàn để hủy — null hóa con trỏ/handle.
  • 06Không viết return std::move(local) — nó phá NRVO thay vì tối ưu thêm.
  • 07Cẩn thận reference/pointer/string_view trỏ vào temporary — lifetime extension không lan truyền qua return hay qua member.
  • 08Nhận object đa hình theo reference/pointer, không bao giờ theo giá trị — tránh object slicing.

Quyết định nhanh

  1. Resource có thể compose từ member RAII có sẵn không? → Có: Rule of Zero, dừng ở đây.
  2. Không — phải tự quản lý thủ công? → Viết đủ Rule of Five, đánh dấu noexcept cho move.
  3. Class không nên cho phép copy? → = delete copy, vẫn giữ move (như DmaChannel ở 0x04).

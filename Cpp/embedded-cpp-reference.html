C++ cho Lập trình Nhúng

OOP, design pattern, container và các từ khóa tối ưu hóa — nhìn từ góc độ chi phí RAM, Flash và tính real-time, không phải C++ "sách giáo khoa".

01

OOP trong lập trình nhúng

OOP trên nhúng không "miễn phí" như trên desktop/server. Mỗi cơ chế — virtual, exception, RTTI — đều có chi phí RAM/Flash/cycle cụ thể, đo được. Câu hỏi không phải "có nên dùng OOP" mà là biết chính xác chi phí của từng cơ chế để chọn đúng chỗ dùng.

Encapsulation — gần như zero-cost

Bọc thanh ghi phần cứng vào class là trường hợp OOP "ăn chắc" nhất trên nhúng: với constexpr + hàm inline nhỏ, compiler dịch thẳng về đúng số lệnh ghi thanh ghi như code C thuần, không sinh thêm overhead.

gpio.hppZero overhead ở -O2
class GpioPin {
public:
    constexpr GpioPin(GPIO_TypeDef* port, uint16_t pin) noexcept
        : port_(port), pin_(pin) {}

    void set()   const noexcept { port_->BSRR = pin_; }
    void reset() const noexcept { port_->BSRR = pin_ << 16; }
    bool read()  const noexcept { return port_->IDR & pin_; }

private:
    GPIO_TypeDef* port_;
    uint16_t pin_;
};

constexpr GpioPin led(GPIOA, GPIO_PIN_5);
led.set();   // -O2: dịch thẳng thành 1 lệnh STR vào BSRR, không có call

Inheritance & chi phí virtual dispatch

Interface trừu tượng cho driver/sensor là chỗ inheritance tỏ ra hữu ích — nhưng virtual có giá cụ thể: mỗi object thêm 1 con trỏ vtable (4 byte trên hệ 32-bit như Cortex-M, 8 byte trên hệ 64-bit), bản thân vtable nằm trong .rodata/flash, và gọi qua con trỏ base là indirect call — 2 lần load thay vì nhảy trực tiếp, compiler không inline được (trừ khi devirtualization tại LTO xác định được kiểu cụ thể).

sensor.hppvtable +4B/objectKhông inline được
class Sensor {
public:
    virtual float read() = 0;
    virtual ~Sensor() = default;
};

class TempSensor : public Sensor {
public:
    float read() override { return value_; }
private:
    float value_;
};

// Sensor* s = &tempSensor;
// s->read();  // load vtable ptr -> load slot -> call: 2 indirect load + 1 branch
  • Tránh virtual trong ISR, hot loop (sampling DMA/ADC tần suất kHz), và bất kỳ đoạn code nào chạy trong critical section (ngắt đang tắt — càng ngắn càng tốt).
  • Virtual hợp lý ở code init/config (chạy một lần lúc boot), dispatch tần suất thấp (command parser, UI), hoặc nơi cần driver có thể hot-swap lúc runtime.
Static vs dynamic polymorphism
Khi kiểu cụ thể đã biết lúc compile-time, CRTP (mục 02) cho polymorphism mà không tốn vtable — đánh đổi bằng code size do mỗi kiểu instantiate riêng. Xem chi tiết ở phần Design Patterns và Template.
Exception & RTTI
Nhiều toolchain bare-metal build với -fno-exceptions -fno-rtti vì exception unwinding cần thêm bảng unwind trong flash (có thể +10–20% code size) và phá tính deterministic về timing. virtual vẫn dùng bình thường khi tắt exception, nhưng dynamic_cast/typeid sẽ không hoạt động.
02

Design Patterns cho nhúng

Các pattern kinh điển vẫn áp dụng được, nhưng cách hiện thực trên nhúng thường lệch khỏi sách GoF — ưu tiên static storage, tránh heap, và luôn tính đến việc code có thể chạy trong ngữ cảnh ISR.

RAII — quản lý resource phần cứng

RAII quan trọng hơn trên nhúng so với application thường, vì "resource" ở đây là thanh ghi, DMA channel, critical section — quên giải phóng không chỉ leak mà có thể khiến phần cứng treo.

critical_section.hppISR-safe
class CriticalSection {
public:
    CriticalSection() noexcept { taskENTER_CRITICAL(); }
    ~CriticalSection() noexcept { taskEXIT_CRITICAL(); }
    CriticalSection(const CriticalSection&) = delete;
    CriticalSection& operator=(const CriticalSection&) = delete;
};

void updateSharedBuffer() {
    CriticalSection guard;   // vào critical section
    // ... thao tác dữ liệu chia sẻ với ISR
}   // tự thoát critical section kể cả khi return sớm

uart_driver.hpp
class UartDriver {

Lưu ý FreeRTOS
Nên gọi instance() lần đầu trong main() — trước vTaskStartScheduler(). Guard variable cho magic-static dựa vào runtime hỗ trợ (__cxa_guard_acquire); khởi tạo trước khi scheduler chạy tránh phụ thuộc cơ chế double-checked locking đó trên MCU nhỏ.

State Machine — cách tiếp cận table-driven cổ điển

FSM là pattern xuất hiện nhiều nhất trong firmware thực tế (protocol parser, quản lý trạng thái sạc/nguồn...). Cách switch/enum không tốn gì ngoài vài lệnh so sánh, chạy tốt trên MCU nhỏ nhất:

charger_fsm.cppKhông heap, không virtual
enum class State { Idle, Charging, Fault };
enum class Event { Start, Overcurrent, Done };

State transition(State s, Event e) {
    switch (s) {
        case State::Idle:
            if (e == Event::Start) return State::Charging;
            break;
        case State::Charging:
            if (e == Event::Overcurrent) return State::Fault;
            if (e == Event::Done) return State::Idle;
            break;
        case State::Fault:
            break;
    }
    return s;
}

Với Embedded Linux hoặc MCU dư flash hơn, std::variant + std::visit (C++17) cho FSM type-safe — mỗi state mang theo đúng dữ liệu của nó, sai kiểu bị bắt lúc compile:

charger_fsm.cppType-safeCode size lớn hơn switch
struct Idle {};
struct Charging { uint32_t startTick; };
struct Fault { uint8_t errorCode; };
using ChargerState = std::variant<Idle, Charging, Fault>;

struct StartEvent { uint32_t tick; };

ChargerState onEvent(const ChargerState& s, const StartEvent& e) {
    return std::visit([&](auto&& cur) -> ChargerState {
        using T = std::decay_t<decltype(cur)>;
        if constexpr (std::is_same_v<T, Idle>)
            return Charging{e.tick};
        else
            return cur;   // event không hợp lệ ở state hiện tại
    }, s);
}

Trên MCU flash rất nhỏ (<64KB) ưu tiên switch/enum — std::visit sinh code dispatch phức tạp hơn đáng kể so với switch thuần.

Observer — callback list không heap

Trong ngữ cảnh ISR gọi callback vào task, std::function là rủi ro: lambda có capture đủ lớn sẽ cấp phát heap. Dùng con trỏ hàm thuần với mảng slot cố định:

observer.hppKhông heapstd::function: rủi ro heap
template <typename... Args>
class StaticObserver {
public:
    using Callback = void(*)(Args...);

    bool subscribe(Callback cb) {
        for (auto& slot : slots_) {
            if (slot == nullptr) { slot = cb; return true; }
        }
        return false;   // hết chỗ — không heap alloc dự phòng
    }
    void notify(Args... args) const {
        for (auto cb : slots_) if (cb) cb(args...);
    }
private:
    std::array<Callback, 4> slots_{};
};

CRTP — static polymorphism

Curiously Recurring Template Pattern cho "interface" mà không tốn vtable — dispatch resolve hoàn toàn lúc compile-time, compiler có thể inline xuyên suốt.

spi_driver.hppNo vtableCompile-time dispatch
template <typename Derived>
class Driver {
public:
    void init() { static_cast<Derived*>(this)->initImpl(); }
    void transmit(std::span<const uint8_t> d) {
        static_cast<Derived*>(this)->transmitImpl(d);
    }
};

class SpiDriver : public Driver<SpiDriver> {
    friend class Driver<SpiDriver>;
    void initImpl() { /* cấu hình SPI */ }
    void transmitImpl(std::span<const uint8_t> d) { /* ghi thanh ghi SPI */ }
};

Đánh đổi: mỗi Derived khác nhau sinh một bản instantiate riêng của Driver<Derived> — nhiều driver type khác nhau đồng nghĩa code size tăng. Chi tiết kỹ thuật giảm bloat ở mục 06.

PIMPL — chủ yếu có giá trị trên Embedded Linux

Khi build shared library (.so) dùng chung giữa nhiều tiến trình — ví dụ daemon giao tiếp qua D-Bus — PIMPL cho phép đổi implementation nội bộ mà không phá ABI của thư viện, đổi lại thêm một lần cấp phát heap + một lớp indirect call cho mỗi truy cập.

Trên bare-metal thường không đáng: không có khái niệm "thư viện chia sẻ giữa nhiều process" nên chi phí PIMPL không bù lại được lợi ích gì.

Object Pool — cấp phát "động" mà không chạm heap

object_pool.hppStatic storage
template <typename T, size_t N>
class ObjectPool {
public:
    T* acquire() {
        for (size_t i = 0; i < N; ++i)
            if (!used_[i]) { used_[i] = true; return &storage_[i]; }
        return nullptr;
    }
    void release(T* obj) {
        size_t i = obj - storage_.data();
        used_[i] = false;
    }
private:
    std::array<T, N> storage_{};
    std::array<bool, N> used_{};
};
03

Containers cho lập trình nhúng

std::vector, std::string, std::map mặc định dùng heap qua std::allocator. Trên hệ chạy liên tục hàng tuần/tháng, alloc/free với size khác nhau liên tục (buffer gói tin UART/network chẳng hạn) là con đường ngắn nhất tới heap fragmentation. Nhiều project bare-metal tắt hẳn heap (không link heap của newlib, hoặc override operator new để assert) — buộc lỗi lộ ra lúc build thay vì rơi ngẫu nhiên sau vài ngày chạy thật.

std::array — thay thế C array, zero overhead

 Stack/static, không heap
std::array<uint8_t, 64> frame{};
frame.at(3);     // bounds-checked, throw nếu tắt exception -> terminate
frame[3];        // không kiểm tra, giống C array thuần
frame.size();    // biết trước lúc compile-time, thường bị tối ưu hết

ETL — Embedded Template Library

Thư viện open-source phổ biến trong giới embedded C++: cung cấp API gần như giống hệt STL (etl::vector, etl::list, etl::map, etl::string...) nhưng backing storage là fixed-capacity khai báo tại compile-time, không đụng heap.

sensor_buffer.cppFixed capacity, không heap
#include "etl/vector.h"

etl::vector<SensorSample, 32> buffer;   // dung lượng cố định 32 phần tử
buffer.push_back({temp, ts});
if (buffer.full()) { /* xử lý tràn theo policy riêng */ }

Ring buffer tự viết — kinh điển cho UART RX/TX

ring_buffer.hppSPSC — ISR ghi, task đọc
template <typename T, size_t N>
class RingBuffer {
    static_assert((N & (N - 1)) == 0, "N phải là lũy thừa của 2 để dùng mask nhanh");
public:
    bool push(const T& v) {
        size_t next = (head_ + 1) & (N - 1);
        if (next == tail_) return false;   // đầy
        buf_[head_] = v;
        head_ = next;
        return true;
    }
    bool pop(T& out) {
        if (head_ == tail_) return false;  // rỗng
        out = buf_[tail_];
        tail_ = (tail_ + 1) & (N - 1);
        return true;
    }
private:
    std::array<T, N> buf_{};
    volatile size_t head_ = 0, tail_ = 0;
};
volatile hay atomic cho head_/tail_?
volatile ngăn compiler cache giá trị trong thanh ghi, đủ dùng cho pattern SPSC kinh điển này trên single-core Cortex-M. Chuẩn mực hơn theo C++11 trở lên là std::atomic<size_t> với memory_order_acquire/release — đúng về mặt chuẩn ngôn ngữ, và trên Cortex-M compile ra cùng load/store thường (không cần LDREX/STREX cho thao tác đơn giản này), tức không đổi chi phí runtime so với volatile.

std::span (C++20) — view không copy

 Non-owning, không copy
void logHex(std::span<const uint8_t> data) {
    for (auto b : data) printf("%02X ", b);
}

uint8_t frame[16];
logHex(frame);   // truyền được array, std::array, hoặc con trỏ+size — không copy

Kiểm tra toolchain có hỗ trợ -std=c++20 trước khi dùng: arm-none-eabi-gcc ≥ 10 hỗ trợ khá đầy đủ; trên Embedded Linux với toolchain Buildroot hiện đại thường không vấn đề.

Static allocator cho STL container
Có thể viết một allocator dùng static memory pool để vẫn dùng API STL quen thuộc (std::vector<T, StaticAllocator<T, N>>) mà không chạm heap thật — hữu ích khi muốn giữ API chuẩn nhưng vẫn kiểm soát bộ nhớ tuyệt đối.
04

Từ khóa tối ưu hóa cho nhúng

Bảy từ khóa dưới đây không "làm code nhanh hơn" một cách ma thuật — chúng cho compiler đủ thông tin để tự tối ưu đúng, và ở vài trường hợp (const, constexpr) quyết định thẳng dữ liệu nằm ở RAM hay Flash.

explicit — chặn implicit conversion

Tác dụngTắt implicit conversion cho constructor 1 tham số (hoặc conversion operator) — compiler ngừng tự động convert kiểu khác sang class này ở call site, bắt buộc gọi constructor tường minh.
Dùng khiClass là wrapper mỏng cho một giá trị nguyên thủy dùng làm ID/handle/tham số (Pin, ChannelId, mili-giây...) — bất kỳ chỗ nào 2 tham số cùng kiểu nguyên thủy (int, uint8_t) có nguy cơ bị nhầm ở nơi gọi.
 Bắt lỗi lúc compile
class Pin {
public:
    explicit Pin(uint8_t number) : number_(number) {}
private:
    uint8_t number_;
};

void configure(Pin p);
configure(5);        // lỗi biên dịch — không cho convert ngầm định
configure(Pin(5));   // OK, tường minh

Rất đáng làm với mọi class wrapper mỏng cho ID/handle (Pin, ChannelId, RegisterAddress...) — nơi dễ vô tình convert nhầm int ở nơi gọi có nhiều overload.

constexpr — tính lúc biên dịch, chi phí runtime bằng 0

Tác dụngYêu cầu compiler đánh giá biểu thức/hàm lúc biên dịch nếu input là hằng số — kết quả trở thành hằng số nằm sẵn trong binary, không tốn cycle runtime để tính lại. Gọi với input không phải hằng số biên dịch, hàm vẫn chạy bình thường như hàm runtime thường.
Dùng khiGiá trị/bảng suy ra hoàn toàn từ input đã biết lúc build — baud rate divisor, CRC/lookup table, kích thước buffer, giá trị cấu hình clock. Bất kỳ phép tính nào không phụ thuộc dữ liệu chỉ có lúc runtime.
 0 cycle runtime
constexpr uint32_t computeBaudDiv(uint32_t clockHz, uint32_t baud) {
    return clockHz / baud;
}
constexpr uint32_t kUsartDiv = computeBaudDiv(84'000'000, 115200);
// Tính lúc BIÊN DỊCH — 0 cycle lúc runtime, giá trị nằm sẵn trong flash

constexpr std::array<uint16_t, 256> makeCrcTable() {
    std::array<uint16_t, 256> table{};
    for (uint32_t i = 0; i < 256; ++i) {
        uint16_t crc = i;
        for (int b = 0; b < 8; ++b)
            crc = (crc & 1) ? (crc >> 1) ^ 0xA001 : crc >> 1;
        table[i] = crc;
    }
    return table;
}
constexpr auto kCrcTable = makeCrcTable();   // 512 byte trong flash, không tính lại lúc chạy

C++11 constexpr chỉ cho một statement return; C++14 trở đi nới lỏng — cho phép loop, biến local, nhiều statement như ví dụ trên. if constexpr (C++17) là biến thể dành cho template, xem mục 06.

inline — gợi ý chèn code, và tránh vi phạm ODR

Tác dụngHai tác dụng độc lập: (1) gợi ý compiler chèn thẳng thân hàm vào nơi gọi thay vì tạo lệnh gọi riêng — chỉ là gợi ý, compiler ở -O2+ tự quyết theo heuristic riêng, không đảm bảo tuyệt đối. (2) cho phép định nghĩa hàm/biến trong header include ở nhiều .cpp mà không vi phạm ODR (multiple definition lúc link).
Dùng khiHàm rất nhỏ, gọi tần suất cao (đọc/ghi thanh ghi, getter/setter) — muốn tránh overhead push/pop và nhảy của lệnh gọi hàm thật; hoặc cần định nghĩa hàm ngay trong file header.
adc.hpp
// Trong header — hàm nhỏ, tần suất gọi cao
inline uint16_t readAdcRaw() {
    return ADC1->DR;
}

Hai vai trò: (1) gợi ý compiler chèn code trực tiếp, tránh overhead gọi hàm (push/pop, nhảy — đáng kể trên MCU tần số thấp/hot loop); (2) cho phép định nghĩa hàm trong header include ở nhiều .cpp mà không vi phạm ODR. Compiler hiện đại ở -O2 trở lên thường tự quyết định dựa trên heuristic riêng — muốn ép buộc dùng __attribute__((always_inline)) (GCC/Clang-specific).

volatile — bắt buộc cho thanh ghi memory-mapped

Tác dụngBuộc compiler đọc/ghi trực tiếp từ bộ nhớ ở mỗi lần truy cập trong code — không được cache giá trị trong thanh ghi CPU hay loại bỏ truy cập tưởng như "thừa". Chỉ có đúng tác dụng này: không đảm bảo atomic, không đảm bảo thứ tự đọc/ghi giữa các biến khác nhau, không đồng bộ giữa nhiều core.
Dùng khiĐọc/ghi thanh ghi memory-mapped (giá trị có thể đổi bởi phần cứng ngoài tầm compiler biết) — hoặc một cờ đơn giản (1 bool/int) chia sẻ giữa ISR và main loop trên single-core. Dữ liệu phức tạp hơn hoặc hệ đa nhân → cần std::atomic.
 Bắt buộc cho MMIO
volatile bool dataReady = false;

void EXTI0_IRQHandler() {
    dataReady = true;   // ISR ghi
}
void mainLoop() {
    while (!dataReady) { /* chờ */ }   // volatile ngăn compiler tối ưu thành vòng lặp vô hạn
    dataReady = false;
}
volatile không phải atomic
volatile chỉ đảm bảo compiler không cache/loại bỏ việc đọc-ghi — không đảm bảo tính atomic, không đảm bảo memory ordering giữa nhiều biến, và không đồng bộ giữa các core trên hệ multi-core. Với dữ liệu phức tạp hơn 1 cờ bool (counter, struct nhiều field), hoặc trên Embedded Linux đa luồng/đa nhân, dùng std::atomic thay vì chỉ volatile.

noexcept — tài liệu hóa, và cho STL container tối ưu

Tác dụngKhai báo hàm không throw exception. Nếu vi phạm (throw xảy ra bên trong), chương trình gọi std::terminate ngay lập tức thay vì unwind stack. Cho phép compiler bỏ code xử lý exception liên quan (bảng unwind), và một số hàm STL — như reallocation của std::vector — chọn dùng move thay vì copy khi biết chắc không có exception giữa chừng.
Dùng khiMove constructor/move assignment — gần như luôn nên đánh dấu noexcept nếu có thể; hoặc bất kỳ hàm nào chắc chắn không throw. Trên project build -fno-exceptions, noexcept chủ yếu mang tính tài liệu hóa.
dma_buffer.hpp
class DmaBuffer {
public:
    DmaBuffer(DmaBuffer&& other) noexcept
        : ptr_(other.ptr_), size_(other.size_) {
        other.ptr_ = nullptr;
    }
private:
    uint8_t* ptr_;
    size_t size_;
};
  • Nhiều project build với -fno-exceptions — khi đó noexcept chủ yếu tài liệu hóa, và cho phép compiler bỏ bảng unwind liên quan.
  • Khi vẫn bật exception: đánh dấu move constructor/move assignment noexcept cho phép std::vector (và container tương tự) dùng move thay vì copy khi resize — nếu move ctor không noexcept, std::vector sẽ copy để giữ strong exception guarantee.

const — global const đi thẳng vào Flash, không tốn RAM

Tác dụngVới biến/mảng global có initializer hằng số: chuyển vị trí lưu trữ từ .data (RAM, phải copy từ flash lúc startup) sang .rodata (đọc thẳng từ flash, 0 byte RAM). Với biến local/tham số: chỉ ngăn code vô tình sửa giá trị — ít ảnh hưởng runtime nhưng giúp compiler tối ưu và code dễ đọc hơn.
Dùng khiMọi bảng dữ liệu/hằng số global không đổi lúc runtime — lookup table, chuỗi log, giá trị cấu hình cố định. Gần như luôn nên dùng, trừ khi thật sự cần ghi đè giá trị lúc runtime.
 const: 0B RAMnon-const: +256B RAM
// KHÔNG const: nằm trong .data — tốn 256 byte RAM,
// và phải copy từ flash sang RAM lúc startup
uint8_t lookupTable[256] = { /* ... */ };

// CÓ const: nằm trong .rodata — link thẳng vào flash,
// 0 byte RAM, không copy lúc boot
const uint8_t lookupTable[256] = { /* ... */ };

Một trong những tối ưu RAM dễ áp dụng nhất và hay bị bỏ sót nhất — trên MCU RAM nhỏ (STM32F4 dòng phổ biến chỉ 128–192KB RAM dù cả MB flash), luôn kiểm tra linker map file (.map) xem bảng dữ liệu lớn có đang nằm nhầm trong .data/.bss hay không.

static — internal linkage & static local

Tác dụngBa ngữ cảnh khác nhau: (1) biến/hàm ở namespace scope → internal linkage, không vào symbol table toàn cục, giảm nguy cơ đụng tên khi link nhiều .cpp. (2) biến local trong hàm → chỉ khởi tạo một lần, giữ giá trị qua các lần gọi, khởi tạo lần đầu thread-safe từ C++11. (3) member của class → thuộc về class chứ không phải từng object, chỉ tồn tại một bản.
Dùng khi(1) Hàm helper chỉ dùng nội bộ một file .cpp. (2) Singleton hoặc giá trị cần "nhớ" giữa các lần gọi mà không muốn lộ ra thành biến global. (3) Hằng số/counter dùng chung giữa mọi instance của class.
 
// static function-scope: internal linkage, không vào symbol table toàn cục
static void handleOverflow() { /* ... */ }

// static local: nền tảng của Meyer's singleton (xem mục 02)
UartDriver& uart() {
    static UartDriver inst;
    return inst;
}
05

Rule of Five

Nếu tự định nghĩa một trong năm hàm — destructor, copy constructor, copy assignment, move constructor, move assignment — cân nhắc định nghĩa (hoặc =default/=delete tường minh) cả năm. Quan trọng trên nhúng vì class thường trực tiếp sở hữu resource phần cứng: DMA channel, UART handle, mutex — hai object cùng nghĩ mình sở hữu một kênh DMA vật lý là bug double-configure/double-free kinh điển.

dma_channel.hppMove-only
class DmaChannel {
public:
    explicit DmaChannel(uint8_t channelId) : id_(channelId) {
        DMA_Configure(id_);
    }
    ~DmaChannel() {
        if (id_ != kInvalid) DMA_Release(id_);
    }

    // Không cho copy — 2 object không thể cùng sở hữu 1 kênh DMA vật lý
    DmaChannel(const DmaChannel&) = delete;
    DmaChannel& operator=(const DmaChannel&) = delete;

    // Cho phép move — chuyển quyền sở hữu
    DmaChannel(DmaChannel&& other) noexcept : id_(other.id_) {
        other.id_ = kInvalid;
    }
    DmaChannel& operator=(DmaChannel&& other) noexcept {
        if (this != &other) {
            if (id_ != kInvalid) DMA_Release(id_);
            id_ = other.id_;
            other.id_ = kInvalid;
        }
        return *this;
    }

private:
    static constexpr uint8_t kInvalid = 0xFF;
    uint8_t id_;
};
Bạn tự khai báoCopy ctor / copy assignMove ctor / move assign
DestructorVẫn sinh (deprecated)Không sinh
Copy ctor hoặc copy assign—Không sinh
Move ctor hoặc move assignBị xóa hẳn (=delete)—

Rule of Zero

Nếu class chỉ chứa các member đã tự quản lý đúng (std::array, kiểu nguyên thủy, hoặc RAII wrapper như DmaChannel ở trên) — không cần viết tay bất kỳ hàm nào trong năm hàm, để compiler tự sinh. Ưu tiên Rule of Zero; chỉ viết tay Rule of Five khi class thật sự trực tiếp sở hữu một resource thô (con trỏ, handle, ID phần cứng).

Ghi chú tương tác với noexcept: move operations nên noexcept khi có thể — xem lại mục 04 về lý do std::vector quan tâm điều này.

06

Template cho lập trình nhúng

Ngoài CRTP (mục 02), template trên nhúng thường dùng cho hai việc: truy cập thanh ghi an toàn kiểu (type-safe), và driver generic không qua vtable. Đổi lại luôn phải cảnh giác với code bloat.

Type-safe register access

register.hppCompile-time inline
template <uintptr_t Address, typename T = uint32_t>
struct Register {
    static T read()  { return *reinterpret_cast<volatile T*>(Address); }
    static void write(T v) { *reinterpret_cast<volatile T*>(Address) = v; }

    template <T Mask>
    static void setBits() { write(read() | Mask); }
};

using GpioaOdr = Register<0x40020014UL>;
GpioaOdr::write(0x20);
GpioaOdr::setBits<0x20>();

Mỗi Register<Address> khác nhau là một type khác nhau tại compile-time — gán nhầm giá trị của GPIOA cho GPIOB (nếu 2 thanh ghi định nghĩa type khác nhau) bị bắt lúc biên dịch, thay vì lỗi runtime khó dò như khi dùng con trỏ void*/uint32_t thô.

Driver generic theo bus — không vtable

temp_sensor.hppNo vtable
template <typename Bus>
class TempSensor {
public:
    explicit TempSensor(Bus& bus) : bus_(bus) {}
    float readCelsius() {
        uint8_t raw[2];
        bus_.read(kAddr, raw, 2);
        return decode(raw);
    }
private:
    Bus& bus_;
    static constexpr uint8_t kAddr = 0x48;
    static float decode(const uint8_t* raw) { return 0.0f; }
};

// không cần base class, resolve tại compile-time

Cảnh báo code bloat & cách giảm

Mỗi tổ hợp tham số template khác nhau sinh một bản code riêng biệt. Trên MCU flash nhỏ (<128KB), dùng template quá rộng cho nhiều type khác nhau có thể khiến flash phình nhanh. Kỹ thuật kinh điển: tách phần logic không phụ thuộc type ra một base class non-template — chỉ phần thật sự cần type-specific mới nằm trong template.

 Giảm code size khi có nhiều N khác nhau
// Base không template — code CHỈ sinh một lần, dùng chung cho mọi N
class RingBufferBase {
protected:
    bool pushImpl(void* buf, size_t elemSize, size_t& head,
                  size_t& tail, size_t capacity, const void* v);
};

// Template chỉ giữ phần phụ thuộc T và N
template <typename T, size_t N>
class RingBuffer : private RingBufferBase {
    // gọi pushImpl() thay vì tự viết lại logic mask/index
};

Explicit instantiation kiểm soát nơi sinh code — tránh mỗi translation unit include header tự sinh lại một bản (linker thường gộp lại nhưng vẫn tốn thời gian biên dịch):

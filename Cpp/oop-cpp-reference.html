01 / 04 · ENCAPSULATION

Đóng gói Encapsulation

> Câu hỏi cốt lõi: Ai được phép đọc/ghi dữ liệu bên trong object?

Đóng gói là gói dữ liệu và hành vi vào chung một class, rồi khóa quyền truy cập trực tiếp vào dữ liệu bằng private/protected. Mọi thao tác buộc phải đi qua method công khai — nơi có thể kiểm tra tính hợp lệ. TemperatureSensor dưới đây không cho ai đọc/ghi thẳng rawADCValue; muốn cập nhật, bắt buộc gọi updateReading(), nơi giá trị được kiểm tra nằm trong dải 12-bit hợp lệ.

encapsulation.cpp
#include <iostream>
#include <stdexcept>

class TemperatureSensor {
private:
    int rawADCValue;
    float calibrationOffset;
    static constexpr float ADC_TO_CELSIUS = 0.125f;

public:
    TemperatureSensor(float offset) : rawADCValue(0), calibrationOffset(offset) {}

    void updateReading(int adcValue) {
        if (adcValue < 0 || adcValue > 4095) {
            throw std::out_of_range("ADC value ngoai dai 12-bit");
        }
        rawADCValue = adcValue;
    }

    float readCelsius() const {
        return rawADCValue * ADC_TO_CELSIUS + calibrationOffset;
    }
};

int main() {
    TemperatureSensor sensor(-2.0f);
    sensor.updateReading(1600);
    std::cout << "Nhiet do: " << sensor.readCelsius() << " C\n";
    // sensor.rawADCValue = 9999;  // LOI BIEN DICH - khong the truy cap truc tiep
    return 0;
}
OutputNhiet do: 198 C
⊘ KHÔNG PHẢI Trừu tượng (mục 02) Đóng gói không phải là "thiết kế giao diện chỉ lộ ra điều cần thiết" — đó là Trừu tượng. Đóng gói thuần túy là cơ chế truy cập (private/public) bên trong một class. Ví dụ trên chưa hề có kế thừa hay lớp trừu tượng nào.
02 / 04 · ABSTRACTION

Trừu tượng Abstraction

> Câu hỏi cốt lõi: Nên lộ ra hành vi gì, giấu đi chi tiết nào?

Trừu tượng là quyết định thiết kế. Cách phổ biến nhất trong C++ là dùng pure virtual function để định nghĩa một "hợp đồng" (contract). ISensor dưới đây không có bất kỳ dữ liệu hay dòng code hiện thực nào — nó chỉ tuyên bố: "một sensor thì đọc được giá trị và có tên". Hàm logSensor() chỉ biết đến ISensor, không hề biết BMP280 giao tiếp I2C ra sao bên dưới.

abstraction.cpp
#include <iostream>

// ISensor la HOP DONG thuan tuy: chi khai bao "lam duoc gi", khong co "lam nhu the nao"
class ISensor {
public:
    virtual float read() = 0;
    virtual const char* name() const = 0;
    virtual ~ISensor() = default;
};

// Mot cach hien thuc cu the - giao tiep I2C that su phuc tap hon nhieu
class BMP280 : public ISensor {
    float simulatedPressure = 1013.25f;
public:
    float read() override { return simulatedPressure; }
    const char* name() const override { return "BMP280"; }
};

// Ham nay CHI phu thuoc vao giao dien ISensor, khong biet gi ve BMP280
void logSensor(ISensor& sensor) {
    std::cout << sensor.name() << " = " << sensor.read() << "\n";
}

int main() {
    BMP280 bmp;
    logSensor(bmp);
    return 0;
}
OutputBMP280 = 1013.25
⊘ KHÔNG PHẢI Đóng gói (mục 01) ISensor thậm chí chẳng có biến private nào để giấu — nó trả lời câu hỏi khác hẳn: "người dùng class cần biết gì để dùng được nó", chứ không phải "ai được đụng vào dữ liệu bên trong". Vì ISensor không thể tạo object trực tiếp, ví dụ cần một lớp cụ thể (BMP280) để chạy được — nhưng trọng tâm ở đây là bản thân hợp đồng ISensor, còn cơ chế kế thừa nó thuộc về mục 03.
03 / 04 · INHERITANCE

Kế thừa Inheritance

> Câu hỏi cốt lõi: Làm sao tái sử dụng & mở rộng code có sẵn?

Kế thừa là việc một class con dùng lại toàn bộ dữ liệu/method của class cha, và bổ sung thêm cái riêng. Đây thuần túy là chuyện tái sử dụng code, xác định lúc biên dịch — chưa liên quan gì đến gọi hàm ảo hay quyết định lúc runtime. SensorBase dưới đây là một class bình thường, không hề trừu tượng, không có virtual nào cả.

inheritance.cpp
#include <iostream>
#include <string>

// SensorBase la lop CU THE - khong truu tuong, khong virtual
class SensorBase {
protected:
    std::string deviceName;
    int errorCount = 0;

public:
    SensorBase(const std::string& name) : deviceName(name) {}

    void logError() {                 // hanh vi dung chung cho MOI sensor
        errorCount++;
        std::cout << "[" << deviceName << "] Loi thu " << errorCount << "\n";
    }

    std::string getName() const { return deviceName; }
};

// HumiditySensor KE THUA toan bo hanh vi tren, khong can viet lai
class HumiditySensor : public SensorBase {
public:
    HumiditySensor() : SensorBase("HumiditySensor-SHT31") {}

    float readRaw() {                 // ham RIENG cua HumiditySensor
        return 65.5f;
    }
};

int main() {
    HumiditySensor h;
    std::cout << h.getName() << ": " << h.readRaw() << "%\n";  // dung lai method ke thua
    h.logError();                     // dung lai method ke thua, KHONG override gi ca
    return 0;
}
OutputHumiditySensor-SHT31: 65.5% [HumiditySensor-SHT31] Loi thu 1
⊘ KHÔNG PHẢI Đa hình (mục 04) Không có con trỏ/tham chiếu lớp cha nào được dùng ở đây, cũng không có virtual. Gọi h.logError() luôn chạy đúng một hàm SensorBase::logError() — trình biên dịch biết chính xác điều đó từ trước, không cần đợi chương trình chạy.
04 / 04 · POLYMORPHISM

Đa hình Polymorphism

> Câu hỏi cốt lõi: Sao cùng một lời gọi lại ra hành vi khác nhau?

Đa hình là khi cùng một lời gọi hàm chạy ra hành vi khác nhau, tùy kiểu thực sự của object lúc runtime — không phải kiểu khai báo. Điều kiện: hàm phải là virtual, và phải gọi qua con trỏ/tham chiếu của lớp cha. So với mục 03, SensorBase giờ được bổ sung virtual float read() = 0;.

polymorphism.cpp
#include <iostream>
#include <vector>
#include <memory>
#include <string>

class SensorBase {
protected:
    std::string deviceName;
public:
    SensorBase(const std::string& name) : deviceName(name) {}
    virtual float read() = 0;      // moi them so voi muc 03
    virtual ~SensorBase() = default;
};

class HumiditySensor : public SensorBase {
public:
    HumiditySensor() : SensorBase("Humidity") {}
    float read() override { return 65.5f; }
};

class PressureSensor : public SensorBase {
public:
    PressureSensor() : SensorBase("Pressure") {}
    float read() override { return 1013.25f; }
};

int main() {
    std::vector<std::unique_ptr<SensorBase>> sensors;
    sensors.push_back(std::make_unique<HumiditySensor>());
    sensors.push_back(std::make_unique<PressureSensor>());

    // CUNG MOT dong "s->read()", nhung ket qua khac nhau tuy loai sensor THUC SU
    for (auto& s : sensors) {
        std::cout << s->read() << "\n";
    }
    return 0;
}
Output65.5 1013.25
⊘ Ranh giới với Kế thừa (mục 03) Ở mục 03, h.logError() gọi trực tiếp qua kiểu cụ thể HumiditySensor — trình biên dịch biết trước hàm nào chạy. Ở đây, ta gọi qua SensorBase* — trình biên dịch KHÔNG biết trước, việc chọn hàm nào chạy được quyết định lúc chương trình thực thi (qua vtable). Đây chính là ranh giới giữa hai tính chất.

Ghi chú: đây là đa hình động (runtime, qua virtual). C++ còn có đa hình tĩnh (compile-time) qua nạp chồng hàm — trình biên dịch chọn đúng hàm ngay lúc biên dịch, không cần vtable, không cần kế thừa:

static_overload.cpp
void show(int x)   { std::cout << "int: "   << x << "\n"; }
void show(float x) { std::cout << "float: " << x << "\n"; }

show(5);      // chon ban int   - quyet dinh LUC BIEN DICH
show(5.0f);   // chon ban float - quyet dinh LUC BIEN DICH
TỔNG HỢP

Cả 4 tính chất trong một hệ thống nhỏ

Trong code thực tế, cả 4 tính chất thường xuất hiện cùng lúc. Đoạn dưới đánh dấu rõ phần nào thuộc tính chất nào — dùng lại đúng ý tưởng của 4 ví dụ trên:

combined.cpp
#include <iostream>
#include <vector>
#include <memory>
#include <string>
#include <cstdint>

// TRUU TUONG: hop dong chung "sensor doc duoc gia tri va co ten"
class ISensor {
public:
    virtual float read() const = 0;
    virtual std::string name() const = 0;
    virtual ~ISensor() = default;
};

// KE THUA: I2CSensorBase dung lai logic dia chi I2C cho moi sensor con
class I2CSensorBase : public ISensor {
protected:
    // DONG GOI: dia chi I2C la chi tiet noi bo, chi lop con duoc dung, ben ngoai khong dung duoc
    uint8_t i2cAddress;
    std::string deviceName;

public:
    I2CSensorBase(uint8_t addr, const std::string& name)
        : i2cAddress(addr), deviceName(name) {}

    std::string name() const override { return deviceName; }
};

class HumiditySensor : public I2CSensorBase {
public:
    HumiditySensor() : I2CSensorBase(0x44, "SHT31-Humidity") {}
    float read() const override { return 65.5f; }
};

class PressureSensor : public I2CSensorBase {
public:
    PressureSensor() : I2CSensorBase(0x76, "BMP280-Pressure") {}
    float read() const override { return 1013.25f; }
};

int main() {
    std::vector<std::unique_ptr<ISensor>> sensors;
    sensors.push_back(std::make_unique<HumiditySensor>());
    sensors.push_back(std::make_unique<PressureSensor>());

    // DA HINH: cung mot dong "s->read()", ket qua khac nhau tuy loai sensor
    for (const auto& s : sensors) {
        std::cout << s->name() << " = " << s->read() << "\n";
    }
    return 0;
}
OutputSHT31-Humidity = 65.5 BMP280-Pressure = 1013.25
TRỪU TƯỢNGISensor — hợp đồng, không data.
KẾ THỪAI2CSensorBase dùng lại cho mọi sensor con.
ĐÓNG GÓIi2cAddress là protected, giấu khỏi bên ngoài.
ĐA HÌNHVòng lặp cuối gọi qua ISensor*.

Kế thừa vs Đa hình

Kế thừa là bạn có một class con dùng lại code cha — quan hệ cố định, biết trước lúc biên dịch. Đa hình là khi bạn gọi qua con trỏ/tham chiếu lớp cha và hành vi chạy thật được quyết định lúc runtime.

→ Có Kế thừa mà không có Đa hình là bình thường (mục 03). Nhưng Đa hình runtime trong C++ luôn cần Kế thừa + virtual làm nền.

Trừu tượng vs Đóng gói

Đóng gói là kỹ thuật: giấu biến, chỉ cho truy cập qua method. Trừu tượng là mức thiết kế: quyết định hành vi nào lộ ra qua interface, giấu đi chi tiết "làm sao".

→ Một class có thể đóng gói cực tốt (toàn bộ dữ liệu private) mà chẳng trừu tượng chút nào — tức là không hề có interface chung nào cả.

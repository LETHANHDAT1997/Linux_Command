Yocto Project — Từ zero đến build image

Tài liệu tổng hợp cách build một Linux distro tùy chỉnh bằng Yocto Project: kiến trúc BitBake/OpenEmbedded, layer, recipe, tới workflow thực hành tạo layer riêng, build image, debug lỗi và đưa lên board thật. Viết cho người đã quen Buildroot/embedded Linux, muốn nắm Yocto ở mức dùng được ngay trong dự án thực tế.

Phần 01 · Nền tảng

Yocto Project là gì?

Yocto không phải một bản Linux distro — nó là một bộ công cụ (framework) để bạn tự build ra distro của riêng mình, đóng gói vừa khít cho phần cứng embedded, từ source code, theo cách lặp lại được (reproducible).

01.1Các thành phần cốt lõi

Khi người ta nói "dùng Yocto", thực chất là đang dùng một tổ hợp nhiều dự án con. Hiểu rõ ai làm gì sẽ giúp đọc lỗi và đọc tài liệu dễ hơn rất nhiều:

Thành phầnVai trò
BitBakeTask executor / build engine — đọc metadata, dựng dependency graph, thực thi task theo đúng thứ tự. Tương tự make nhưng hoạt động ở quy mô "toàn bộ distro" thay vì một project.
OpenEmbedded-Core (OE-Core)Tập metadata lõi dùng chung — hàng nghìn recipe, class nền tảng (autotools, cmake, kernel...). Do Yocto Project và OpenEmbedded Project đồng duy trì.
PokyReference distribution — gói sẵn BitBake + OE-Core + meta-poky + meta-yocto-bsp thành một combo dùng được ngay. Khi bạn git clone poky, đây là thứ bạn tải về.
MetadataToàn bộ "mô tả" cách build: recipe (.bb), append (.bbappend), class (.bbclass), config (.conf). Yocto không hardcode gì cả — mọi thứ là metadata.
LayerCách tổ chức metadata thành các "module" độc lập, xếp chồng và override lẫn nhau theo priority. Đây là cơ chế mở rộng chính của Yocto.
💡
Điểm khác biệt cốt lõi

Buildroot build ra một rootfs theo cấu hình bạn chọn trong menuconfig. Yocto build ra các package nhị phân độc lập (rpm/ipk/deb) rồi mới lắp ráp thành image — giống một distro Linux thật (như Debian) nhưng do chính bạn kiểm soát từng package. Đây là lý do Yocto có SDK export, có thể update từng package riêng lẻ, và scale tốt hơn khi dự án lớn dần.

01.2So sánh nhanh với Buildroot

Vì bạn đã quen Buildroot, bảng dưới đây dùng nó làm điểm neo để nắm Yocto nhanh hơn:

Buildroot

  • Cấu hình qua menuconfig (Kconfig) — một file .config duy nhất
  • Build tuyến tính, ít trừu tượng, source → rootfs trực tiếp
  • Không có khái niệm package nhị phân độc lập (mặc định)
  • Học nhanh, phù hợp dự án nhỏ/vừa, ít board
  • Khó tái sử dụng metadata giữa nhiều dự án khác nhau
  • Rebuild lại gần như toàn bộ khi đổi cấu hình sâu

Yocto Project

  • Cấu hình qua recipe/layer/class — nhiều file, có cấu trúc
  • Build theo package (rpm/ipk/deb) rồi lắp thành image
  • Có package management thật, có thể publish package feed
  • Đường cong học dốc hơn, nhưng scale tốt cho team lớn, nhiều board
  • Layer tái sử dụng được giữa nhiều dự án/nhiều SoC
  • Shared State Cache (sstate) giúp rebuild cực nhanh khi đổi nhỏ

Kinh nghiệm chung: nếu chỉ build cho 1 board, ít thay đổi, ưu tiên tốc độ ra sản phẩm → Buildroot vẫn rất hợp lý. Nếu công ty maintain nhiều dòng SoC/board, nhiều team cùng đóng góp package, cần SDK cho dev app, hoặc cần bảo trì lâu dài với security update từng package → Yocto đáng đầu tư thời gian học hơn.

Phần 02 · Nền tảng

Chuẩn bị môi trường

Yocto build toolchain và hầu hết package từ source, nên yêu cầu host khá nặng. Chuẩn bị đúng ngay từ đầu sẽ tránh được phần lớn lỗi khó chịu ở bước sau.

02.1Yêu cầu hệ thống

Hệ điều hành
Linux native (Ubuntu LTS khuyến nghị). Windows: dùng WSL2
Dung lượng ổ đĩa
Tối thiểu 50GB, thực tế nên có 150–200GB (sstate + downloads + nhiều build)
RAM
≥ 8GB tối thiểu, khuyến nghị 16GB+ cho build song song mượt
CPU
Càng nhiều core càng tốt — BitBake song song hoá rất tốt
📌
Về phiên bản Yocto

Tính đến thời điểm viết tài liệu này (07/2026), bản LTS mới nhất là Yocto 6.0 "Wrynose" (phát hành 04/2026, kế nhiệm 5.0 "Scarthgap"). Bản 5.0 "Scarthgap" (04/2024) vẫn còn được hỗ trợ chính thức đến 04/2028 và vẫn rất phổ biến trong các BSP vendor hiện có. Nếu layer BSP của bạn chỉ hỗ trợ tới Scarthgap, dùng Scarthgap — đừng cố ép lên bản mới hơn.

02.2Cài package cần thiết (Ubuntu/Debian)

Danh sách package tối thiểu để build headless (không cần GUI host):

terminal
sudo apt update
sudo apt install -y build-essential chrpath cpio debianutils diffstat \
  file gawk gcc git iputils-ping libacl1 libcrypt-dev locales python3 \
  python3-git python3-jinja2 python3-pexpect python3-pip python3-subunit \
  socat texinfo unzip wget xz-utils zstd

Đảm bảo locale en_US.UTF-8 được bật (Yocto yêu cầu locale này để tránh lỗi parse metadata):

terminal
locale -a | grep -i "en_US.utf8"
# Nếu chưa có:
sudo locale-gen en_US.UTF-8
sudo update-locale LANG=en_US.UTF-8
⚠️
Không build với quyền root

BitBake chủ động từ chối chạy bằng sudo/root — đây là chủ đích, không phải bug. Build bằng user thường; chỉ dùng sudo cho bước cài package hệ thống.

Phần 03 · Nền tảng

Build lần đầu (Quick Start)

Đi thẳng vào một build thật với QEMU trước, để có cảm giác về workflow ngay — phần khái niệm sâu hơn sẽ theo sau ở các phần 5–10.

03.1Lấy source Poky

terminal
git clone git://git.yoctoproject.org/poky
cd poky
# Chọn nhánh/release — ví dụ dùng LTS Scarthgap (ổn định, hỗ trợ tới 04/2028):
git checkout scarthgap
# Hoặc dùng LTS mới nhất Wrynose:
# git checkout wrynose
🌐
Nếu mạng chặn giao thức git://

Một số mạng doanh nghiệp/ISP chặn port của giao thức git://. Dùng HTTPS thay thế: git clone https://git.yoctoproject.org/poky, hoặc mirror trên GitHub: git clone https://github.com/yoctoproject/poky.git.

03.2Khởi tạo môi trường build

terminal
source oe-init-build-env
# → tự động cd vào ./build (tạo mới nếu chưa có) và nạp toàn bộ
#   biến môi trường + PATH cần thiết cho bitbake

Lệnh này thực hiện 3 việc quan trọng: tạo thư mục build/, sinh ra build/conf/local.conf và build/conf/bblayers.conf với giá trị mặc định nếu chưa tồn tại, và thêm các script của BitBake (bitbake, bitbake-layers, devtool...) vào PATH cho phiên terminal hiện tại. Mỗi terminal mới đều phải source lại file này trước khi chạy bitbake.

03.3Build image đầu tiên

terminal (đang ở trong poky/build)
bitbake core-image-minimal
⏱️
Lần build đầu tiên rất lâu

Lần đầu, Yocto tải và build toàn bộ toolchain (gcc, binutils, glibc...) từ source trước khi build bất kỳ package nào — có thể mất 1–4 giờ tuỳ CPU/mạng. Các lần build sau nhanh hơn nhiều nhờ sstate-cache (phần 04 giải thích cơ chế này). Đây là hành vi bình thường, không phải build bị treo — cứ để chạy.

03.4Chạy thử bằng QEMU

terminal
runqemu qemux86-64

Mặc định MACHINE trong local.conf vừa tạo là qemux86-64, nên lệnh build ở trên đã build sẵn image cho kiến trúc này. runqemu tự tìm image mới build gần nhất khớp với MACHINE hiện tại và khởi động QEMU với network + rootfs đã cấu hình sẵn. Thoát QEMU bằng cách đóng cửa sổ hoặc Ctrl+C trong terminal đã chạy lệnh.

  • Muốn build cho kiến trúc khác? Sửa MACHINE ?= "qemux86-64" trong build/conf/local.conf — các giá trị built-in khác: qemuarm64, qemuarm, qemumips64, qemuriscv64...
  • Build cho board thật cần thêm BSP layer tương ứng — xem Phần 15.
Phần 04 · Nền tảng

Cấu trúc thư mục

Nắm được cây thư mục giúp đọc log lỗi và tìm output nhanh hơn rất nhiều — đây là bản đồ bạn sẽ quay lại liên tục.

04.1Thư mục poky/ (source)

poky/ ├── bitbake/ # Source code của BitBake engine + toàn bộ script bitbake-* ├── meta/ # OpenEmbedded-Core: hàng nghìn recipe + class nền tảng ├── meta-poky/ # Metadata riêng của distro "poky" (policy mặc định) ├── meta-yocto-bsp/ # BSP mẫu cho vài board tham khảo (beaglebone, genericx86...) ├── meta-selftest/ # Layer phục vụ test nội bộ của BitBake/OE-Core ├── scripts/ # devtool, runqemu, oe-* helper scripts ├── documentation/ # Source của toàn bộ tài liệu chính thức └── oe-init-build-env # Script bạn source() để khởi tạo build/

04.2Thư mục build/ (nơi mọi thứ được sinh ra)

build/ ├── conf/ │ ├── local.conf # Config máy cục bộ: MACHINE, DISTRO, package cần thêm... │ ├── bblayers.conf # Danh sách layer đang active trong build này │ └── templateconf.cfg ├── downloads/ # Source đã fetch về (tarball, git clone...) — dùng chung mọi recipe ├── sstate-cache/ # Shared State Cache — output đã build sẵn của từng task └── tmp/ ├── work/<arch>/<recipe>/<version>/ # Nơi từng recipe được fetch/unpack/build │ └── temp/log.do_<task> # Log chi tiết từng task — chỗ đầu tiên cần xem khi lỗi ├── deploy/images/<machine>/ # Output cuối: .wic, .ext4, kernel Image, dtb... ├── deploy/rpm|ipk|deb/ # Package nhị phân đã build, theo format đã chọn ├── deploy/sdk/ # SDK/toolchain export (populate_sdk) ├── sysroots-components/ # Header/lib đã cài để recipe khác DEPENDS vào └── stamps/ # File đánh dấu task nào đã chạy xong (BitBake dựa vào đây để skip)
Thư mụcKhi nào cần vào
tmp/work/.../temp/log.do_compileBuild lỗi ở bước compile — xem log chi tiết tại đây trước tiên
tmp/deploy/images/<machine>/Cần lấy file image để flash lên board thật
tmp/work/.../${S}Muốn xem/sửa trực tiếp source đã patch của một recipe
sstate-cache/Muốn chia sẻ cache build giữa nhiều máy/dự án (xem Phần 10)
⚡
sstate-cache hoạt động ra sao?

Mỗi task của mỗi recipe được BitBake "chấm hash" dựa trên toàn bộ input ảnh hưởng tới nó (source, biến cấu hình, dependency...). Nếu hash không đổi so với lần trước, BitBake tải kết quả đã build sẵn từ sstate-cache thay vì build lại từ đầu. Đây là lý do lần build thứ 2 trở đi nhanh hơn lần đầu rất nhiều, kể cả sau khi xoá tmp/.

Phần 05 · Cơ chế BitBake

BitBake hoạt động thế nào

BitBake không "chạy một script build" — nó đọc toàn bộ metadata, hiểu quan hệ phụ thuộc giữa hàng nghìn recipe, rồi tự quyết định thứ tự thực thi. Hiểu mô hình task này là chìa khoá để debug mọi lỗi build sau này.

05.1Task pipeline của một recipe

Mỗi recipe khi build đều đi qua một chuỗi task chuẩn (mỗi task là do_<tên>). BitBake chạy tuần tự theo dependency, cache lại kết quả từng task vào sstate:

fetchtải source
→
unpackgiải nén
→
patcháp patch
→
configure./configure, cmake
→
compilemake
→
installmake install → ${D}
→
packageđóng gói rpm/ipk/deb
→
populate_sysrootcho recipe khác DEPENDS
TaskÝ nghĩa
do_fetchTải source theo SRC_URI (git/http/local file...) về downloads/
do_unpackGiải nén/copy source vào thư mục làm việc ${WORKDIR}, thường là ${S}
do_patchÁp các file patch liệt kê trong SRC_URI (thường có prefix file://)
do_configureChạy bước cấu hình build (autoreconf/configure, cmake...) — phụ thuộc class inherit
do_compileBiên dịch — thường gọi make/ninja trong ${B}
do_installCài output vào thư mục ảo ${D} (destdir) — không cài vào hệ thống thật
do_packageQuét ${D}, chia thành các sub-package theo PACKAGES/FILES
do_populate_sysrootExport header/lib cần thiết để recipe khác DEPENDS vào recipe này lúc build
do_rootfs(Chỉ recipe image) Lắp toàn bộ package đã build thành rootfs hoàn chỉnh

05.2Mô hình thực thi

Khi bạn gõ bitbake core-image-minimal, BitBake: (1) parse tất cả file .conf/.bbclass/.bb/.bbappend trong các layer đang active, (2) với target yêu cầu, dựng cây phụ thuộc đầy đủ — cả phụ thuộc build-time (DEPENDS) lẫn runtime (RDEPENDS), (3) với mỗi task trong cây, tính hash dựa trên input ảnh hưởng nó, so với sstate-cache để quyết định build lại hay tái sử dụng, (4) thực thi các task độc lập song song (theo BB_NUMBER_THREADS) trong lúc vẫn tôn trọng thứ tự phụ thuộc.

05.3Lệnh BitBake thường dùng

LệnhCông dụng
bitbake <target>Build một recipe hoặc image tới hết pipeline
bitbake -c <task> <target>Chạy một task cụ thể, vd -c compile, -c devshell, -c menuconfig
bitbake -f -c <task> <target>Ép chạy lại task dù sstate đã có sẵn (force)
bitbake -c clean <target>Xoá output build của recipe (giữ lại source đã fetch)
bitbake -c cleansstate <target>Như trên, cộng thêm xoá luôn sstate-cache của recipe → build lại từ đầu
bitbake -c cleanall <target>Như cleansstate, cộng thêm xoá cả source đã tải → fetch lại từ đầu
bitbake -e <target>Dump toàn bộ biến đã resolve — thường dùng với grep ^VAR=
bitbake -g <target>Sinh dependency graph (task-depends.dot, pn-depends.dot)
bitbake -kTiếp tục build các target khác dù có target lỗi (keep-going)
bitbake -v / -DVerbose / debug log — thêm nhiều -D để tăng độ chi tiết
bitbake-layers show-layersLiệt kê layer đang active + priority
bitbake-layers show-recipesLiệt kê recipe khả dụng, kèm layer nào cung cấp
ví dụ tra biến
# Xem giá trị SRC_URI đã resolve của recipe busybox
bitbake -e busybox | grep ^SRC_URI=

# Xem toàn bộ giá trị mặc định của một biến toàn cục (không cần target)
bitbake -e | grep ^MACHINE=
Phần 06 · Cơ chế BitBake

Layers

Layer là đơn vị tổ chức metadata chính của Yocto — thứ giúp bạn "cắm vào / rút ra" cả một mảng chức năng (một BSP, một tập ứng dụng, một policy distro) mà không đụng vào code của layer khác.

06.1Cấu trúc một layer

meta-mylayer/ ├── conf/ │ └── layer.conf # Bắt buộc — khai báo layer này với BitBake ├── recipes-core/ │ └── busybox/ │ └── busybox_%.bbappend ├── recipes-myapp/ │ └── myapp/ │ ├── myapp_1.0.bb │ └── files/ │ └── 0001-fix-something.patch ├── COPYING.MIT └── README

Chỉ có conf/layer.conf là bắt buộc — đây là thứ biến một thư mục thường thành một "layer" mà BitBake nhận diện được:

meta-mylayer/conf/layer.conf
# Thêm layer này vào đường tìm kiếm của BitBake
BBPATH .= ":${LAYERDIR}"

# Pattern tìm recipe/append trong layer này
BBFILES += "${LAYERDIR}/recipes-*/*/*.bb \
            ${LAYERDIR}/recipes-*/*/*.bbappend"

# Tên định danh layer, dùng trong bblayers.conf và khi debug
BBFILE_COLLECTIONS += "mylayer"
BBFILE_PATTERN_mylayer = "^${LAYERDIR}/"

# Priority — số càng cao càng được ưu tiên khi 2 layer cùng cung cấp 1 recipe
BBFILE_PRIORITY_mylayer = "6"

# Layer này cần layer "core" (OE-Core) đã có sẵn
LAYERDEPENDS_mylayer = "core"

# Chỉ tương thích với các release đã liệt kê — bitbake sẽ cảnh báo nếu không khớp
LAYERSERIES_COMPAT_mylayer = "scarthgap walnascar wrynose"

06.2Kích hoạt layer qua bblayers.conf

Layer tồn tại trên đĩa không có nghĩa là nó được dùng — phải khai báo trong build/conf/bblayers.conf của build hiện tại:

build/conf/bblayers.conf
POKY_BBLAYERS_CONF_VERSION = "2"
BBPATH = "${TOPDIR}"
BBFILES ?= ""

BBLAYERS ?= " \
  /home/user/poky/meta \
  /home/user/poky/meta-poky \
  /home/user/poky/meta-yocto-bsp \
  /home/user/poky/meta-mylayer \
  "

Trong thực tế, dùng bitbake-layers thay vì sửa tay để tránh lỗi cú pháp:

terminal
bitbake-layers add-layer ../meta-mylayer
bitbake-layers remove-layer meta-mylayer
bitbake-layers show-layers          # xem layer + priority hiện tại
bitbake-layers show-appends         # xem recipe nào đang bị .bbappend chỉnh sửa
bitbake-layers show-overlayed       # xem recipe nào bị override bởi layer priority cao hơn

06.3Ba loại layer thường gặp

LoạiChứa gìVí dụ
BSP layerMachine config, kernel/bootloader recipe riêng cho SoC/boardmeta-raspberrypi, meta-ti, layer BSP của vendor SoC
Distro layerPolicy toàn distro: init system, C library, security policy...meta-poky, meta-openembedded/meta-oe
Software layerRecipe cho ứng dụng/thư viện cụ thể của dự ánlayer riêng của bạn cho app JKC, hoặc meta-qt6
🔎
Tìm layer có sẵn

Trước khi tự viết, luôn kiểm tra OpenEmbedded Layer Index — phần lớn thư viện/BSP phổ biến đã có layer cộng đồng maintain sẵn, tiết kiệm rất nhiều thời gian so với viết recipe từ đầu.

Phần 07 · Cơ chế BitBake

Recipes chi tiết

Recipe (.bb) là đơn vị mô tả "build cái gì, từ đâu, thành gì" cho một package. Đây là phần bạn sẽ viết/đọc nhiều nhất khi làm việc thực tế với Yocto.

07.1Quy ước đặt tên file

Tên file quyết định PN (package name) và PV (package version) tự động:

quy ước
myapp_1.2.0.bb    →  PN = "myapp"   PV = "1.2.0"
myapp_git.bb      →  PN = "myapp"   PV = "git" (thường kèm PV = "1.0+git${SRCPV}" trong file)

07.2Biến quan trọng

BiếnÝ nghĩa
DESCRIPTION / SUMMARYMô tả package — hiện trong metadata package quản lý (rpm/ipk)
LICENSEGiấy phép (vd "MIT", "GPL-2.0-only") — bắt buộc, dùng cho audit license
LIC_FILES_CHKSUMChecksum của file license trong source — BitBake báo lỗi nếu nội dung license đổi mà chưa cập nhật, chống thay đổi license âm thầm
SRC_URINguồn: có thể là http://, git://, file:// (patch/file cục bộ trong layer), gộp nhiều dòng được
SThư mục chứa source sau khi unpack (mặc định ${WORKDIR}/${BPN}-${PV})
BThư mục build — khác S khi build out-of-tree (cmake thường vậy)
DThư mục cài đặt ảo (destdir) lúc do_install — không phải hệ thống thật
DEPENDSPhụ thuộc lúc build (recipe khác phải build/populate_sysroot xong trước)
RDEPENDS:${PN}Phụ thuộc lúc chạy (package khác phải có mặt trên rootfs)
PACKAGESDanh sách sub-package tách ra từ 1 recipe (vd tách -dev, -dbg, -staticdev)
FILES:${PN}-xxxFile nào thuộc sub-package nào

07.3Ví dụ: recipe cho project dùng Makefile thuần

recipes-myapp/myapp/myapp_1.0.bb
DESCRIPTION = "Ứng dụng đo cảm biến JKC"
LICENSE = "MIT"
LIC_FILES_CHKSUM = "file://LICENSE;md5=0835ade698e0bcf8506ecda2f7b4f302"

SRC_URI = "git://github.com/myorg/myapp.git;protocol=https;branch=main"
SRCREV = "a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2"
PV = "1.0+git${SRCPV}"

S = "${WORKDIR}/git"

DEPENDS = "zlib"
RDEPENDS:${PN} = "bash"

do_compile() {
    oe_runmake
}

do_install() {
    install -d ${D}${bindir}
    install -m 0755 ${B}/myapp ${D}${bindir}
}

Vì recipe này không inherit class build system nào, do_compile/do_install phải viết tay hoàn toàn. oe_runmake là wrapper của make đã tự truyền đúng cờ cross-compile (CC, CFLAGS...).

07.4Ví dụ: recipe autotools & cmake

Nếu project dùng autotools hoặc CMake chuẩn, inherit class tương ứng và gần như không cần viết task nào — class tự cung cấp do_configure/do_compile/do_install đúng chuẩn:

recipe dùng autotools (./configure)
DESCRIPTION = "Thư viện log dùng autotools"
LICENSE = "BSD-3-Clause"
LIC_FILES_CHKSUM = "file://COPYING;md5=..."

SRC_URI = "http://example.com/liblog-2.1.tar.gz"
SRC_URI[sha256sum] = "..."

inherit autotools
EXTRA_OECONF = "--disable-static"
recipe dùng CMake
DESCRIPTION = "Thư viện xử lý ảnh dùng CMake"
LICENSE = "Apache-2.0"
LIC_FILES_CHKSUM = "file://LICENSE;md5=..."

SRC_URI = "git://github.com/myorg/libimg.git;protocol=https;branch=main"
SRCREV = "..."
S = "${WORKDIR}/git"

inherit cmake
EXTRA_OECMAKE = "-DBUILD_TESTS=OFF -DUSE_NEON=ON"
🔑
Dấu "..." trong checksum nghĩa là gì?

Các giá trị md5=... / SRC_URI[sha256sum] = "..." ở trên là placeholder minh hoạ — checksum thật phụ thuộc đúng nội dung file license/source của từng project. Mẹo thực tế: cứ để giá trị sai hoặc để trống, chạy bitbake <recipe>, BitBake sẽ báo lỗi kèm theo checksum đúng ngay trong log — copy giá trị đó dán vào recipe là xong, không cần tự tính tay.

✅
Ưu tiên inherit class có sẵn

Chỉ viết do_compile/do_install tay khi thực sự cần (Makefile tự chế, script build riêng). Với autotools/cmake/meson chuẩn, luôn inherit class tương ứng — ít code hơn, đồng nhất với toàn bộ OE-Core, và tự động hưởng các cải tiến/patch của class khi upgrade Yocto.

Phần 08 · Cơ chế BitBake

Classes & inherit

Class (.bbclass) là nơi đóng gói logic dùng chung — thay vì copy-paste task giữa hàng trăm recipe, viết một lần rồi inherit.

08.1base.bbclass — mọi recipe đều có sẵn

base.bbclass được BitBake tự động inherit vào mọi recipe, không cần khai báo — đây là nơi định nghĩa các task rỗng mặc định (do_fetch, do_unpack, do_patch...) và các hàm tiện ích dùng chung (oe_runmake, event handler...).

08.2Các class thường dùng nhất

ClassCung cấp gì
autotoolsdo_configure chạy autoreconf + ./configure, do_compile/do_install gọi make chuẩn
cmakeToàn bộ pipeline configure/compile/install qua CMake + Ninja, hỗ trợ cross-compile sẵn qua toolchain file
kernelTask riêng cho build Linux kernel: do_kernel_configme, tạo package kernel-image/kernel-modules/kernel-dev tự động
kernel-yoctoCơ chế "config fragment" cho kernel Yocto — merge nhiều fragment .cfg thành 1 .config cuối
systemdTự cài/enable unit file systemd (SYSTEMD_SERVICE) đúng chỗ
pkgconfigĐảm bảo file .pc được cài đúng sysroot cho recipe khác dùng pkg-config
python3native / setuptools3Build package Python bằng interpreter native (chạy trên host) hoặc target
imageClass nền cho mọi recipe image (core-image-*) — lắp package thành rootfs
allarchĐánh dấu recipe không phụ thuộc kiến trúc CPU (script, config, data file thuần)

08.3Viết class riêng

Khi nhiều recipe trong dự án cần chung một đoạn logic (vd: cùng cách nhúng version build vào binary, cùng bước ký firmware), gom vào 1 class riêng:

meta-mylayer/classes/buildstamp.bbclass
do_install:append() {
    echo "Built: ${DATETIME} rev ${SRCREV}" > ${D}${sysconfdir}/build-info
}
dùng trong recipe bất kỳ
inherit buildstamp

Lưu ý do_install:append() — cú pháp :append/:prepend/:remove là override syntax hiện tại của BitBake (thay cho cú pháp gạch dưới cũ _append đã lỗi thời từ nhiều release trước), dùng để thêm vào một task đã tồn tại thay vì ghi đè toàn bộ.

Phần 09 · Cơ chế BitBake

.bbappend — chỉnh recipe có sẵn mà không sửa gốc

Rất hiếm khi bạn sửa trực tiếp recipe trong meta/ hay BSP layer vendor — thay vào đó, dùng .bbappend trong layer riêng để "vá thêm" từ ngoài. Đây là cách làm chuẩn giúp layer của bạn không bao giờ xung đột khi vendor cập nhật layer gốc.

09.1Quy tắc đặt tên & vị trí

File .bbappend phải cùng tên với recipe gốc (không tính version), và nằm đúng path tương đối giống layer gốc (vd cùng nằm dưới recipes-core/busybox/):

quy ước tên file
# Khớp mọi version của busybox:
recipes-core/busybox/busybox_%.bbappend

# Chỉ khớp đúng version 1.36.1:
recipes-core/busybox/busybox_1.36.1.bbappend

09.2Ví dụ: thêm patch vào recipe có sẵn

meta-mylayer/recipes-core/busybox/busybox_%.bbappend
# Cho BitBake biết tìm file patch trong thư mục con cùng tên recipe,
# đặt cạnh file .bbappend này (vd: recipes-core/busybox/busybox/0001-...patch)
FILESEXTRAPATHS:prepend := "${THISDIR}/${PN}:"

SRC_URI += "file://0001-fix-watchdog-timeout.patch"

THISDIR là thư mục chứa chính file .bbappend đang chạy; dấu := ép expand ngay lập tức (immediate expansion) vì THISDIR chỉ đúng tại thời điểm parse file này.

09.3Ví dụ: thêm file cấu hình / service riêng

meta-mylayer/recipes-connectivity/openssh/openssh_%.bbappend
FILESEXTRAPATHS:prepend := "${THISDIR}/${PN}:"
SRC_URI += "file://sshd_config_custom"

do_install:append() {
    install -m 0644 ${WORKDIR}/sshd_config_custom ${D}${sysconfdir}/ssh/sshd_config
}
⚠️
Đừng dùng = khi bạn muốn "thêm vào"

SRC_URI = "..." (dấu = thường) sẽ ghi đè toàn bộ giá trị gốc, xoá mất source gốc của recipe. Trong .bbappend, gần như luôn dùng += hoặc :append để bổ sung, không thay thế.

Phần 10 · Cơ chế BitBake

local.conf — Biến cấu hình quan trọng

build/conf/local.conf là nơi cấu hình build cho máy cục bộ của bạn — không nên đưa vào git chung của layer, vì nó khác nhau giữa các máy/người.

BiếnÝ nghĩaVí dụ
MACHINEBoard/target đang build choMACHINE = "raspberrypi4-64"
DISTROPolicy distro áp dụng (init system, libc...)DISTRO = "poky"
IMAGE_INSTALL:appendThêm package vào image — chú ý khoảng trắng đầu chuỗiIMAGE_INSTALL:append = " htop nano"
PACKAGE_CLASSESFormat package nhị phânPACKAGE_CLASSES ?= "package_ipk"
BB_NUMBER_THREADSSố task BitBake chạy song songBB_NUMBER_THREADS = "8"
PARALLEL_MAKECờ -j truyền cho make bên trong mỗi taskPARALLEL_MAKE = "-j 8"
DL_DIRNơi lưu source đã fetch — trỏ ra ngoài để share giữa nhiều buildDL_DIR = "/data/yocto-shared/downloads"
SSTATE_DIRNơi lưu sstate-cache — trỏ ra ngoài để share tương tựSSTATE_DIR = "/data/yocto-shared/sstate-cache"
EXTRA_IMAGE_FEATURESBật tính năng tiện dev (debug-tweaks = login root không cần password)EXTRA_IMAGE_FEATURES ?= "debug-tweaks"
💾
Luôn trỏ DL_DIR / SSTATE_DIR ra ngoài build/

Nếu bạn maintain nhiều project/branch Yocto (rất phổ biến khi làm nhiều board hoặc nhiều version firmware), đặt DL_DIR và SSTATE_DIR vào một thư mục dùng chung ngoài mọi build/ sẽ tiết kiệm rất nhiều băng thông và thời gian — mỗi build/ mới tận dụng lại cache của các build trước thay vì tải/build lại từ đầu.

ví dụ local.conf tối thiểu cho một dự án thật
MACHINE = "my-custom-board"
DISTRO = "poky"
PACKAGE_CLASSES = "package_ipk"

DL_DIR = "/data/yocto-shared/downloads"
SSTATE_DIR = "/data/yocto-shared/sstate-cache"

BB_NUMBER_THREADS = "${@oe.utils.cpu_count()}"
PARALLEL_MAKE = "-j ${@oe.utils.cpu_count()}"

EXTRA_IMAGE_FEATURES ?= "debug-tweaks"
IMAGE_INSTALL:append = " htop nano openssh"
🆕
Thay đổi từ Yocto 6.0 "Wrynose"

Từ bản 6.0 trở đi, local.conf mặc định sinh ra gọn hơn hẳn so với các bản trước — nhiều thiết lập (như bật root login) giờ được quản lý qua cơ chế "config fragment" mới (bitbake-config-build enable-fragment ...) thay vì các dòng comment sẵn trong file như trước. Cách viết biến trực tiếp vào local.conf như bảng trên vẫn hoạt động bình thường ở 6.0 và được hầu hết layer/tài liệu hiện có sử dụng — đây vẫn là cách nắm chắc nhất khi mới học.

Phần 11 · Thực hành

Tạo layer + recipe riêng từ A đến Z

Ráp toàn bộ kiến thức phần 6–10 thành một luồng thực hành trọn vẹn: tạo layer riêng, viết recipe cho một app tối giản, rồi build một image tuỳ chỉnh có chứa app đó. Chạy tuần tự các bước dưới trong poky/build.

11.1Tạo & kích hoạt layer

terminal
cd ~/poky
bitbake-layers create-layer ../meta-mylayer
bitbake-layers add-layer ../meta-mylayer
bitbake-layers show-layers   # xác nhận meta-mylayer đã xuất hiện

11.2Viết recipe "hello" tối giản

Tạo cấu trúc thư mục cho recipe, nguồn C được nhúng thẳng trong layer (không cần server git ngoài):

meta-mylayer/recipes-example/hello/ ├── hello_1.0.bb └── files/ ├── hello.c └── Makefile
meta-mylayer/recipes-example/hello/files/hello.c
#include <stdio.h>

int main(void)
{
    printf("Hello from meta-mylayer!\n");
    return 0;
}
meta-mylayer/recipes-example/hello/files/Makefile
CC ?= gcc
CFLAGS ?= -Wall

hello: hello.c
	$(CC) $(CFLAGS) -o hello hello.c

clean:
	rm -f hello
meta-mylayer/recipes-example/hello/hello_1.0.bb
DESCRIPTION = "Recipe demo — ứng dụng Hello World tối giản"
LICENSE = "MIT"
LIC_FILES_CHKSUM = "file://${COMMON_LICENSE_DIR}/MIT;md5=0835ade698e0bcf8506ecda2f7b4f302"

SRC_URI = "file://hello.c \
           file://Makefile"

S = "${WORKDIR}"

do_compile() {
    oe_runmake
}

do_install() {
    install -d ${D}${bindir}
    install -m 0755 hello ${D}${bindir}
}

BitBake tự tìm file:// trong thư mục files/ cạnh recipe (một trong các đường dẫn mặc định của FILESPATH), nên không cần khai báo FILESEXTRAPATHS ở đây.

11.3Build thử recipe độc lập

terminal
bitbake hello
# Kiểm tra output đã cài đúng chưa:
find tmp/work/*/hello/1.0/image -name hello

11.4Tạo image tuỳ chỉnh chứa "hello"

Thay vì sửa local.conf (chỉ đúng trên máy bạn), cách chuẩn khi làm dự án thật là tạo recipe image riêng — kế thừa core-image-minimal rồi thêm package, để build ra bất kỳ máy nào cũng cho kết quả giống nhau:

meta-mylayer/recipes-core/images/mylayer-image.bb
require recipes-core/images/core-image-minimal.bb

DESCRIPTION = "Image tuỳ chỉnh cho dự án — kế thừa core-image-minimal + app riêng"

IMAGE_INSTALL += "hello"

11.5Build & kiểm chứng trên QEMU

terminal
bitbake mylayer-image
runqemu qemux86-64

Trong QEMU, đăng nhập root (không cần password nếu EXTRA_IMAGE_FEATURES có debug-tweaks), rồi chạy thử:

trong QEMU
root@qemux86-64:~# hello
Hello from meta-mylayer!
🎯
Đây chính là vòng lặp làm việc hằng ngày với Yocto

Viết/sửa recipe → bitbake <target> để build riêng lẻ và kiểm tra nhanh → thêm vào image recipe khi ổn → build image đầy đủ → test trên QEMU hoặc board thật. Với thay đổi nhỏ, sstate-cache khiến bước lặp lại nhanh hơn build đầu rất nhiều.

Phần 12 · Thực hành

Kernel & U-Boot trong Yocto

Phần này nối trực tiếp với nền tảng bare-metal/kernel bạn đã có — khác biệt lớn nhất so với build kernel tay là Yocto quản lý config qua fragment thay vì sửa .config trực tiếp.

12.1linux-yocto & cơ chế config fragment

Recipe linux-yocto (và các biến thể) dùng class kernel-yocto: thay vì cung cấp một file .config đầy đủ, bạn cung cấp các fragment nhỏ (chỉ các CONFIG_* muốn bật/tắt), rồi tool merge lại thành .config cuối. Cách này giúp fragment tái sử dụng được giữa nhiều board/kernel version khác nhau.

meta-mylayer/recipes-kernel/linux/linux-yocto_%.bbappend
FILESEXTRAPATHS:prepend := "${THISDIR}/linux-yocto:"

SRC_URI += "file://enable-can.cfg"
meta-mylayer/recipes-kernel/linux/linux-yocto/enable-can.cfg
CONFIG_CAN=y
CONFIG_CAN_RAW=y
CONFIG_CAN_C_CAN=y

12.2Workflow sửa kernel nhanh với devtool

Khi cần debug/sửa kernel source trực tiếp (không chỉ đổi config), devtool là công cụ đúng — tránh phải hiểu hết cơ chế patch/fragment ngay từ đầu:

terminal
devtool modify virtual/kernel
# → checkout source kernel thật ra workspace/sources/linux-yocto để sửa trực tiếp

cd workspace/sources/linux-yocto
# sửa code, hoặc: bitbake virtual/kernel -c menuconfig

devtool build virtual/kernel

# deploy thẳng qua SSH lên board đang chạy để test nhanh, không cần re-flash:
devtool deploy-target virtual/kernel root@192.168.1.50

# khi đã ổn, đưa thay đổi thành patch chính thức vào layer:
devtool finish virtual/kernel meta-mylayer

12.3Recipe cho kernel module out-of-tree

Vì bạn đang tìm hiểu sâu về driver — đây là cách đóng gói một module .ko tự viết thành recipe Yocto, dùng module.bbclass:

meta-mylayer/recipes-kernel/hello-mod/hello-mod_0.1.bb
SUMMARY = "Kernel module demo"
LICENSE = "GPL-2.0-only"
LIC_FILES_CHKSUM = "file://COPYING;md5=..."

inherit module

SRC_URI = "file://hello-mod.c \
           file://Makefile \
           file://COPYING"
S = "${WORKDIR}"

KERNEL_MODULE_AUTOLOAD += "hello-mod"
files/Makefile (mẫu chuẩn cho module out-of-tree)
obj-m := hello-mod.o
SRC := $(shell pwd)

all:
	$(MAKE) -C $(KERNEL_SRC) M=$(SRC)

modules_install:
	$(MAKE) -C $(KERNEL_SRC) M=$(SRC) modules_install

clean:
	rm -f *.o *~ core .depend .*.cmd *.ko *.mod.c
	rm -f Module.markers Module.symvers modules.order

module.bbclass tự truyền KERNEL_SRC/KERNEL_VERSION và toolchain đúng chuẩn vào make — bạn chỉ cần Makefile theo đúng mẫu trên. KERNEL_MODULE_AUTOLOAD khiến module tự modprobe lúc boot.

12.4U-Boot (tóm tắt)

Tương tự kernel, U-Boot được cấu hình chủ yếu qua biến trong machine .conf:

conf/machine/my-board.conf
PREFERRED_PROVIDER_u-boot = "u-boot"
UBOOT_MACHINE = "my_board_defconfig"

Muốn patch source U-Boot thì hoàn toàn giống cách làm với kernel/recipe thường: tạo u-boot_%.bbappend trong layer riêng và thêm patch qua SRC_URI +=.

Phần 13 · Thực hành

Debug & Troubleshooting

Phần lớn thời gian làm việc thực tế với Yocto là đọc lỗi build. Nắm vững vài công cụ dưới đây giúp rút ngắn đáng kể thời gian debug.

13.1devshell — vào đúng môi trường build để debug tay

terminal
bitbake -c devshell myapp

Mở một terminal mới (mặc định xterm) đã set sẵn chính xác mọi biến môi trường (CC, CFLAGS, PATH trỏ vào cross-toolchain...) và cwd tại ${S}/${B} — y hệt lúc BitBake chạy do_compile. Cực hữu ích để thử tay từng lệnh configure/make khi build tự động báo lỗi khó hiểu.

13.2Đọc log & tra biến

terminal
# Log chi tiết của task lỗi (đường dẫn BitBake in ra khi báo lỗi):
cat tmp/work/*/myapp/1.0/temp/log.do_compile

# Tra giá trị cuối cùng (đã resolve) của 1 biến cho 1 recipe:
bitbake -e myapp | grep ^EXTRA_OECONF=

# Xem toàn bộ task đã/chưa chạy của 1 recipe:
bitbake -c listtasks myapp

13.3Lỗi thường gặp

Phần 14 · Thực hành

SDK / Toolchain

Không phải lúc nào cũng cần build lại toàn bộ image chỉ để phát triển một ứng dụng — Yocto có thể export riêng một cross-toolchain đóng gói sẵn (SDK) để dev app độc lập với build chính.

14.1Standard SDK

terminal
bitbake core-image-minimal -c populate_sdk
# Output: tmp/deploy/sdk/*.sh — installer standalone

./tmp/deploy/sdk/poky-glibc-x86_64-core-image-minimal-*.sh
source /opt/poky/6.0/environment-setup-*
# Từ giờ $CC, $CXX, $PKG_CONFIG_PATH... đã trỏ đúng cross-toolchain
$CC myapp.c -o myapp

14.2Extensible SDK (eSDK)

Bản mở rộng của SDK — nhúng kèm cả devtool và một phần build system, cho phép thêm/sửa recipe ngay trong SDK mà không cần checkout lại toàn bộ Yocto:

terminal
bitbake core-image-minimal -c populate_sdk_ext

Phù hợp khi muốn giao cho team dev ứng dụng một bộ công cụ độc lập, không cần họ clone/build cả poky để chỉ sửa 1 app.

Phần 15 · Thực hành

Build cho board thật

QEMU tốt để học và test nhanh, nhưng mục tiêu cuối cùng luôn là một board thật. Khác với Buildroot (thường chỉnh trực tiếp defconfig kernel/bootloader trong cây build), Yocto kỳ vọng phần cứng được mô tả qua một BSP layer có cấu trúc rõ ràng.

15.1Tìm BSP layer có sẵn

Trước khi tự viết, luôn kiểm tra xem SoC/board đã có layer cộng đồng hoặc vendor cung cấp chưa, qua OpenEmbedded Layer Index. Phần lớn SoC phổ biến (NXP, TI, ST, Rockchip, Allwinner, Broadcom...) đều đã có layer chính thức hoặc cộng đồng maintain.

terminal
cd ~/poky
git clone https://github.com/vendor/meta-vendor-bsp.git
bitbake-layers add-layer ../meta-vendor-bsp
# Kiểm tra dependency của layer (thường cần thêm meta-openembedded):
cat meta-vendor-bsp/conf/layer.conf | grep LAYERDEPENDS

Sau đó chỉ cần đổi MACHINE trong local.conf sang giá trị layer BSP định nghĩa (xem trong meta-vendor-bsp/conf/machine/*.conf), rồi build như bình thường:

build/conf/local.conf
MACHINE = "vendor-board-name"

15.2Khi chưa có layer sẵn — machine .conf tối thiểu

Nếu phải tự viết BSP layer cho một board chưa được hỗ trợ, phần lõi là file conf/machine/<tên-machine>.conf. Đây là ví dụ minh hoạ (thực tế sẽ cần nhiều tinh chỉnh hơn tuỳ SoC):

meta-mylayer/conf/machine/my-board.conf
#@TYPE: Machine
#@NAME: My Custom Board
#@DESCRIPTION: Cortex-A53 SoC, 1GB RAM

MACHINEOVERRIDES =. "my-board:"

PREFERRED_PROVIDER_virtual/kernel = "linux-yocto"
PREFERRED_VERSION_linux-yocto ?= "6.6%"
KERNEL_IMAGETYPE = "Image"
KERNEL_DEVICETREE = "vendor/my-board.dtb"

PREFERRED_PROVIDER_u-boot = "u-boot"
UBOOT_MACHINE = "my_board_defconfig"

SERIAL_CONSOLES = "115200;ttyS0"
MACHINE_FEATURES = "usbhost wifi"

IMAGE_FSTYPES = "wic wic.bmap ext4"

15.3Lấy output để flash

Sau khi build xong, image nằm ở tmp/deploy/images/<machine>/ — thường gồm kernel Image/zImage, device tree .dtb, rootfs (.ext4, .wic...). Cách flash cụ thể (dd, fastboot, JTAG, U-Boot qua TFTP...) phụ thuộc hoàn toàn vào bootloader/SoC, thường được layer BSP vendor tài liệu hoá kèm sẵn.

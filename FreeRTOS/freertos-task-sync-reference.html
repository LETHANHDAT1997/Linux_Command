FreeRTOS · Task Synchronization

Đồng Bộ Hoá Giữa Các Task

Khi nhiều task chạy song song, chúng cần phối hợp theo ba nhu cầu cơ bản: loại trừ tương hỗ (ai được vào tài nguyên chung trước), báo hiệu sự kiện (việc gì vừa xảy ra), và truyền dữ liệu (chuyển cái gì từ task này sang task khác). Chọn sai cơ chế cho từng nhu cầu là nguồn gốc phổ biến nhất của priority inversion, deadlock và race condition trong firmware thực tế.

Task A block tại xSemaphoreTake() / ulTaskNotifyTake() — ISR hoặc task khác Give()/Notify() để đánh thức, gần như tức thời.

Mutex & Recursive Mutex

Mutex là một semaphore nhị phân đặc biệt có khái niệm ownership: task nào Take() thì chỉ task đó được Give() lại, và FreeRTOS tự áp dụng priority inheritance cho task đang giữ mutex.

Dùng khi
  • Bảo vệ một tài nguyên hoặc cấu trúc dữ liệu dùng chung giữa nhiều task (biến toàn cục, thanh ghi ngoại vi, file...).
  • Cần đảm bảo tính nguyên tử cho một chuỗi thao tác đọc-sửa-ghi trên tài nguyên đó.
shared_resource.c
SemaphoreHandle_t xMutex;

void vSetupMutex(void) {
    xMutex = xSemaphoreCreateMutex();
}

void vSharedResourceTask(void *pvParameters) {
    for (;;) {
        if (xSemaphoreTake(xMutex, pdMS_TO_TICKS(100)) == pdTRUE) {
            /* Truy cập tài nguyên dùng chung */
            xSemaphoreGive(xMutex);
        }
    }
}

/* Recursive mutex: dùng khi cùng 1 task cần Take() lồng nhau
   (vd hàm A gọi hàm B, cả hai cùng cần lock) */
SemaphoreHandle_t xRMutex = xSemaphoreCreateRecursiveMutex();
xSemaphoreTakeRecursive(xRMutex, portMAX_DELAY);
xSemaphoreGiveRecursive(xRMutex);
Lưu ý — Không dùng mutex trong ISR (khái niệm "ownership" không có ý nghĩa trong ngữ cảnh interrupt). Priority inheritance chỉ giải quyết priority inversion ở dạng "bounded" — vẫn nên giữ đoạn code trong mutex càng ngắn càng tốt.
Báo hiệu

Binary Semaphore

Cờ hiệu nhị phân không có khái niệm ownership — bất kỳ task/ISR nào cũng có thể Give(), bất kỳ task nào cũng có thể Take().

Dùng khi
  • Báo hiệu một sự kiện one-shot, đặc biệt là từ ISR sang task (vd: DMA nhận xong một frame qua SPI).
  • Đồng bộ hai task theo kiểu rendezvous đơn giản, không cần truyền dữ liệu kèm theo.
spi_isr.c
SemaphoreHandle_t xBinSem;

void vSetup(void) {
    xBinSem = xSemaphoreCreateBinary();
}

/* Chạy trong ISR context khi SPI DMA nhận xong dữ liệu từ RC522 */
void HAL_SPI_RxCpltCallback(SPI_HandleTypeDef *hspi) {
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;
    xSemaphoreGiveFromISR(xBinSem, &xHigherPriorityTaskWoken);
    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

void vProcessTask(void *pvParameters) {
    for (;;) {
        if (xSemaphoreTake(xBinSem, portMAX_DELAY) == pdTRUE) {
            /* Xử lý tag RFID vừa đọc xong */
        }
    }
}
Lưu ý — Đừng dùng binary semaphore để bảo vệ tài nguyên chia sẻ (mutual exclusion) — vì không có priority inheritance nên dễ dính priority inversion không kiểm soát được. Nếu chỉ báo hiệu 1-1 giữa ISR và một task cụ thể, Task Notification thường nhanh hơn và tốn ít RAM hơn.
Báo hiệu

Counting Semaphore

Semaphore giữ một bộ đếm giới hạn trong [0, uxMaxCount] — Give() tăng đếm, Take() giảm đếm và block nếu đếm bằng 0.

Dùng khi
  • Quản lý một pool tài nguyên có N phần tử (N buffer DMA, N kết nối, N slot trống trong mảng...).
  • Đếm số sự kiện đã xảy ra mà task xử lý có thể chưa kịp tiêu thụ hết.
buffer_pool.c
SemaphoreHandle_t xPoolSem;
#define NUM_BUFFERS 4

void vSetup(void) {
    xPoolSem = xSemaphoreCreateCounting(NUM_BUFFERS, NUM_BUFFERS);
}

void vAcquireBuffer(void) {
    xSemaphoreTake(xPoolSem, portMAX_DELAY);  /* giảm đếm, chờ nếu hết buffer */
    /* lấy 1 buffer từ pool */
}

void vReleaseBuffer(void) {
    /* trả buffer về pool */
    xSemaphoreGive(xPoolSem);  /* tăng đếm */
}
Gợi ý — Counting semaphore chỉ đếm "số lượng khả dụng", không mang dữ liệu. Nếu task cần biết cụ thể buffer/gói tin nào đã sẵn sàng, dùng Queue thay vì chỉ đếm.
Truyền dữ liệu

Queue

Hàng đợi FIFO copy dữ liệu (theo giá trị, không phải con trỏ) an toàn giữa các task/ISR có ngữ cảnh thực thi khác nhau.

Dùng khi
  • Cần truyền dữ liệu thật sự, không chỉ báo hiệu — mô hình producer/consumer kinh điển.
  • Nhiều producer cùng ghi vào một consumer duy nhất, hoặc ngược lại.
rfid_pipeline.c
QueueHandle_t xDataQueue;

typedef struct {
    uint8_t  uid[4];
    uint32_t timestamp;
} RfidTag_t;

void vSetup(void) {
    xDataQueue = xQueueCreate(8, sizeof(RfidTag_t));
}

/* Task đọc SPI, gửi dữ liệu vào queue */
void vReaderTask(void *pvParameters) {
    RfidTag_t tag;
    for (;;) {
        /* ... đọc tag từ RC522 qua SPI ... */
        xQueueSend(xDataQueue, &tag, pdMS_TO_TICKS(50));
    }
}

/* Task xử lý, nhận dữ liệu từ queue */
void vProcessorTask(void *pvParameters) {
    RfidTag_t tag;
    for (;;) {
        if (xQueueReceive(xDataQueue, &tag, portMAX_DELAY) == pdTRUE) {
            /* xử lý tag */
        }
    }
}
Gợi ý — Dùng xQueueSendFromISR / xQueueReceiveFromISR trong ISR (nhớ portYIELD_FROM_ISR sau đó). Queue độ dài 1 kết hợp xQueueOverwrite() tạo thành một "mailbox" giữ giá trị mới nhất — hữu ích cho dữ liệu kiểu trạng thái (vd nhiệt độ mới nhất) thay vì phải xử lý từng giá trị cũ.
Báo hiệu

Event Group

Một nhóm tối đa 24 bit dùng làm cờ hiệu, cho phép một hoặc nhiều task chờ tổ hợp AND/OR của nhiều điều kiện từ nhiều nguồn khác nhau.

Dùng khi
  • Một task cần chờ nhiều điều kiện cùng lúc trước khi tiếp tục (vd: chờ cả Wi-Fi connected và sensor calibrated).
  • Nhiều task khác nhau cùng cần biết về cùng một sự kiện (broadcast), điều mà Task Notification không làm được.
sync_flags.c
EventGroupHandle_t xEventGroup;
#define BIT_WIFI_CONNECTED   (1 << 0)
#define BIT_SENSOR_READY     (1 << 1)

void vSetup(void) {
    xEventGroup = xEventGroupCreate();
}

void vWifiTask(void *pvParameters) {
    /* ... kết nối wifi xong ... */
    xEventGroupSetBits(xEventGroup, BIT_WIFI_CONNECTED);
}

void vMainTask(void *pvParameters) {
    /* Chờ CẢ HAI điều kiện (AND) trước khi tiếp tục */
    EventBits_t bits = xEventGroupWaitBits(
        xEventGroup,
        BIT_WIFI_CONNECTED | BIT_SENSOR_READY,
        pdTRUE,   /* xoá bit sau khi nhận */
        pdTRUE,   /* true = AND (chờ tất cả), false = OR (chờ 1 trong các bit) */
        portMAX_DELAY);
}
Lưu ý — xEventGroupSetBitsFromISR không set bit trực tiếp — nó nhờ Timer Service (daemon) task xử lý nên có độ trễ nhỏ. Nếu cần tốc độ tối đa từ ISR cho một target cụ thể, Task Notification (chế độ eSetBits) nhẹ hơn.
Báo hiệu

Task Notification

Mỗi task có sẵn một giá trị 32-bit tích hợp ngay trong TCB — không cần tạo object riêng như semaphore hay queue, nên nhanh hơn và tốn ít RAM hơn đáng kể.

Dùng khi
  • Báo hiệu 1-1 (một nguồn → một task cụ thể) và cần tốc độ/hiệu năng tối đa.
  • Có thể thay thế binary semaphore, counting semaphore (xClearCountOnExit = pdFALSE), event group dạng 32-bit (eSetBits), hoặc queue độ dài 1 (eSetValueWithOverwrite).
notify_task.c
TaskHandle_t xProcessTaskHandle;

/* ISR: gửi thông báo nhẹ, không cần tạo object riêng */
void HAL_SPI_RxCpltCallback(SPI_HandleTypeDef *hspi) {
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;
    vTaskNotifyGiveFromISR(xProcessTaskHandle, &xHigherPriorityTaskWoken);
    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

void vProcessTask(void *pvParameters) {
    xProcessTaskHandle = xTaskGetCurrentTaskHandle();
    for (;;) {
        ulTaskNotifyTake(pdTRUE, portMAX_DELAY);  /* giống binary semaphore, nhanh hơn */
        /* xử lý */
    }
}
Lưu ý — Giới hạn lớn nhất: chỉ nhắm tới đúng một task (theo TaskHandle_t), không dùng được khi nhiều task cùng cần chờ chung một sự kiện — lúc đó quay lại Event Group hoặc semaphore.
Kỹ thuật khác

Critical Section & Suspend Scheduler

taskENTER_CRITICAL() / taskEXIT_CRITICAL() tắt ngắt để đảm bảo một đoạn code chạy nguyên tử, không bị chen ngang bởi ISR hay context switch.

Dùng khi
  • Thao tác cực ngắn trên một biến/cấu trúc đơn giản, kể cả khi cần an toàn với chính ISR.
  • Chi phí tạo và quản lý một mutex riêng cho thao tác đó là không đáng.
atomic_counter.c
uint32_t sharedCounter;

void vIncrementCounter(void) {
    taskENTER_CRITICAL();
    sharedCounter++;   /* thao tác cực ngắn, an toàn với cả ISR */
    taskEXIT_CRITICAL();
}
Lưu ý — Không bao giờ gọi API có thể block (vTaskDelay, xSemaphoreTake với timeout > 0...) bên trong critical section. Giữ càng ngắn càng tốt — mỗi micro giây trong đó cộng thêm vào interrupt latency của toàn hệ thống. Cần thao tác dài hơn nhưng không chặn ISR? Dùng vTaskSuspendAll() / xTaskResumeAll() — tạm dừng scheduler (không context-switch) nhưng ISR vẫn chạy bình thường.
Kỹ thuật khác

Gatekeeper Task

Thay vì nhiều task tranh nhau một mutex để truy cập tài nguyên, gom mọi yêu cầu qua một Queue — chỉ một task duy nhất ("gatekeeper") thực sự chạm vào tài nguyên đó.

Dùng khi
  • Serialize quyền truy cập một tài nguyên (UART, flash, EEPROM...) mà không muốn quản lý mutex/priority inversion trực tiếp.
  • Điển hình nhất: gom log từ nhiều task về một điểm ghi UART duy nhất.
log_gatekeeper.c
#define LOG_MSG_LEN 96
typedef struct { char text[LOG_MSG_LEN]; } LogMsg_t;

QueueHandle_t xLogQueue;  /* item = LogMsg_t */

/* Task duy nhất được quyền dùng UART log */
void vLogGatekeeperTask(void *pvParameters) {
    LogMsg_t msg;
    for (;;) {
        if (xQueueReceive(xLogQueue, &msg, portMAX_DELAY) == pdTRUE) {
            HAL_UART_Transmit(&huart1, (uint8_t *)msg.text, strlen(msg.text), 100);
        }
    }
}

/* Các task khác chỉ gửi message vào queue, không đụng UART trực tiếp */
void vLog(const char *fmt) {
    LogMsg_t msg;
    strncpy(msg.text, fmt, LOG_MSG_LEN - 1);
    msg.text[LOG_MSG_LEN - 1] = '\0';
    xQueueSend(xLogQueue, &msg, 0);
}
Gợi ý — Đánh đổi là thêm một task + một queue (tốn RAM hơn một mutex đơn thuần), nhưng đổi lại thiết kế rất rõ ràng, dễ audit, và loại bỏ hoàn toàn priority inversion vì không có "lock" nào cả.

Lỗi thường gặp

Phần lớn bug đồng bộ trong RTOS đến từ 5 nguyên nhân này.

Priority Inversion

Dùng binary semaphore như một lock cho tài nguyên chia sẻ giữa các task khác priority. Task priority thấp giữ semaphore có thể bị task priority trung bình chen ngang, khiến task priority cao phải chờ vô thời hạn. Fix: dùng Mutex (có priority inheritance) khi cần mutual exclusion.

Deadlock

Hai task cùng cần giữ hai mutex nhưng lock theo thứ tự ngược nhau. Fix: luôn lock theo một thứ tự cố định, xuyên suốt toàn bộ codebase.

Quên dùng biến thể FromISR

Gọi xQueueSend thay vì xQueueSendFromISR bên trong interrupt handler → assert hoặc hành vi không xác định. Fix: luôn dùng API có hậu tố FromISR trong ISR, và gọi portYIELD_FROM_ISR() ngay sau đó nếu cần.

Giữ Critical Section quá lâu

Tăng interrupt latency của toàn hệ thống, có thể khiến các ràng buộc thời gian thực khác bị miss deadline. Fix: giữ critical section ở mức vài dòng lệnh, không hơn.

Dùng Mutex trong ISR

Mutex có khái niệm "ownership" gắn với một task cụ thể, nên không có ý nghĩa (và không được hỗ trợ) trong ngữ cảnh ISR. Fix: dùng binary semaphore hoặc task notification để báo hiệu từ ISR.
